# 集成检查与独立终审

> 状态：PLANNED。集成负责人负责候选与检查；终审由未承担相应模块实现的审核者负责。人员不足时，实施者必须单独进行一次按证据重读的审查，并披露“未完成独立人员复核”。不自动启用子智能体。

## 1. 集成顺序与阻塞处理

1. 固定共同提交、I0 DTO 与 JSON 夹具；先验证各工作包可单独编译/测试。
2. A/B 接真实能力与编译，E 接最小产品入口，F 跑首批记录，形成 I1 候选。
3. C 接具体执行与成果；E 接验收面板；F 用公共判定器核对产品结论。
4. D 接局部修复；校验图修改与重跑原子性，E/F 复验审批、拒绝、取消、预算和新证据。
5. 对已集成提交做相关回归、完整源码检查、生产构建和真实桌面流程，生成候选制品及摘要。
6. 终审只针对这一个候选提交/制品核对结论。审查发现问题交原工作线修复，替换候选后重跑受影响检查；不无限重复无关全套测试。

如果某线阻塞，其他线继续使用 G0 契约完成纯逻辑、组件和评测准备。只能将被阻塞的真实接线标为未验收，不能用模拟 provider 替换生产并宣称该阶段通过。

## 2. 验证命令与适用范围

下列为后续实施检查命令，本次文档编写不执行业务构建/测试。PowerShell 执行，每个功能工作区使用各自构建缓存；命令退出码、开始结束时间、实际测试数量与 ignored 项都要记录。

后端改动后，在 `backend` 目录做必需检查：

```powershell
cargo fmt
cargo fmt --check
cargo check -j 1
cargo test -j 1 proofloop -- --test-threads=1
```

`proofloop` 过滤名是拟新增测试命名约定；实施后必须检查匹配测试数量大于 0。0 tests 不能作为通过证据。每次最小改动先执行对应行为测试，再检查编译，不通过就不扩大变更。

集成候选在仓库根目录执行公共 workspace 检查：

```powershell
cargo fmt --all --check
cargo check --workspace -j 1
cargo test --workspace --all-targets -j 1 -- --test-threads=1
cargo build -p yilian-backend --bin yilian-server -j 1
git diff --check
```

前端在 `frontend` 目录执行；依赖已安装则不重复安装：

```powershell
npm.cmd test -- --run --maxWorkers=1 --minWorkers=1
npm.cmd run build
```

现有端到端 runner 读取 `YILIAN_E2E_BACKEND_BINARY`，否则使用根目录 target/debug/yilian-server.exe。必须先构建当前候选并指向正确二进制，不能拿旧缓存冒充新提交。以工作区根目录、默认 target 为例：

```powershell
$env:YILIAN_E2E_BACKEND_BINARY = (Resolve-Path '.\target\debug\yilian-server.exe').Path
Push-Location frontend
npm.cmd run test:e2e
Pop-Location
```

如果设置了独立 CARGO_TARGET_DIR，就改用该目录中本次生成的二进制并记录摘要。U3.1 绑定回归示例：

```powershell
$env:YILIAN_E2E_TYPED_U31 = '1'
Push-Location frontend
npm.cmd run test:e2e
Pop-Location
Remove-Item Env:YILIAN_E2E_TYPED_U31
```

上述模式选择变量不能残留到下一项测试；执行前核对当前进程的相关 E2E 模式设置，避免误跑另一个分支。证行专项拟新增为 `YILIAN_E2E_PROOFLOOP=1`，由 F 在 `core-paths.mjs` 接入后才能执行，未接入时记录 NOT_IMPLEMENTED，不能把默认套件成功当作专项已运行。

Tauri 相关检查与真实窗口运行：

```powershell
cargo check -p yi-lian-qian-yan -j 1
npm.cmd run tauri:build
```

构建成功仅证明可生成制品。还需启动真实窗口，核对进程/窗口、实际数据、授权与取消、保存重开和产物可读。安装包生命周期和两设备云验收仍属原 v1.1 发布范围，不由本专项测试代替。

## 3. 阶段门槛

| 门槛 | 最低证据 | 不接受的替代物 |
|---|---|---|
| G0 契约 | DTO/JSON 一致、文件所有权、实际环境/能力清单、共同基线 | 只有口头分工 |
| G1 编译执行 | C01–C12 必要用例、真实 LLM、真实 MCP、保存重开、审批/拒绝/取消 | 仅模型输出 TaskGraph JSON、仅本地夹具 |
| G2 目标验收 | V01–V09、真实产物、错误验收负对照、human_pending | 只有节点 succeeded 或模型自评 |
| G3 局部修复 | R01–R11、完整首次失败→提案→确认→新执行→新报告 | 重试脚本只改最终状态 |
| G4 产品评测 | U01–U10、30 任务规定次数的实际覆盖/缺口、可复算统计、候选制品 | 只有截图、历史测试总数、未运行模板 |
| G5 独立终审 | 候选提交/制品与全部证据关联、缺口有结论 | 以功能线自述代替回查 |

I1 范围交付只要求 G0/G1 和相应终审，不要求 G2/G3/G4 的完整数据；报告必须写明 `accepted_scope=I1`。完整证行专项交付才要求全部门槛。若阈值未达标，可如实发布技术实验报告，但不能记录“研发指标全部达成”。

## 4. 原始建议覆盖与终审矩阵

| 原始建议/关键缺口 | 责任与阶段 | 审查方法 |
|---|---|---|
| 能力约束自动编排 | A/B，I1 | 从真实 registry ID 回查生成图，不存在能力负例零调用 |
| 输出结构来源 | A，I1 | 原始 MCP 声明到投影到绑定路径逐段核对；未知 schema 不猜测 |
| 自动类型化数据流 | B，I1 | 检查 literal/required 覆盖、直接依赖与实际下游参数 |
| 模型候选不直接执行 | B/集成，I1 | 候选/确认链路没有工具副作用，执行只进入 Gateway |
| 以目标为中心的成果判断 | C，I2 | 节点成功但缺成果的负例必须失败 |
| 来源证据关联 | C，I2 | goal version、graph revision、execution、artifact digest 对应 |
| 有限修复 | D，I3 | 次数、token/时间预算、权限、旧历史、无关节点均复核 |
| 真实产品闭环 | E，I1–I4 | 从正式入口完成操作，不能仅用 API/脚本绕过确认页面 |
| 量化实验 | F，I0–I4 | 任务/预算冻结、三组同判定、原始数据和脚本复算 |
| 恢复对照 | F/D，I3–I4 | B2 与 BR 相同初始图和故障，不用无限重试获取提升 |
| 成功经验回流 | 本轮只使用历史作为人工参考 | 明确长期经验学习未实施，不凭未来规划加分 |
| 独立分支/仓库边界 | 集成负责人 | 公共本体范围；私有服务、后台与冻结 V2 无专项改动 |
| 不重复实现基础设施 | 各线，I5 | 无第二执行器、审批库、画布、成果平台或通用框架 |
| 首轮止于 I1 | I1 任务负责人 | 交付后停止，后续任务单独分配 |

审查源码还需确认：capability 快照无凭据、旧 API/SSE 兼容、既有 loop/cancel 保护保留、绑定快照不读最新输出、编译失败不落假成功、修复不修改目标条件。

## 5. 结果状态与结论

每条检查只能使用有定义的状态：

- `PASS`：本次真实运行满足预期，证据位置可查。
- `FAIL`：实际运行不满足要求；注明现象、影响和复现。
- `BLOCKED`：缺具体外部条件，检查无法开始或完成；注明需要什么。
- `NOT_TESTED`：尚未运行；不含隐含通过。
- `HUMAN_PENDING`：必须由用户/独立设备/人工质量判断完成的环节尚未完成。

终审结果使用以下之一，附交付范围：

| 结论 | 条件 |
|---|---|
| `PROOFLOOP_SCOPE_ACCEPTED` | 指定范围全部必需门槛通过；明确 I1、I2 或 I3 完整档 |
| `NEEDS_FIX` | 存在已确认功能、授权、数据或假成功问题 |
| `ACCEPTANCE_INCOMPLETE` | 未发现足以否定实现的已确认问题，但真实运行/数据/人工门槛未完成 |

专项结论不使用 `READY_FOR_RELEASE`。原 v1.1 的独立发布检查仍由原发布流程做最终判断。

## 6. 每条工作线的交接格式

交接内容应包含：

1. 基线 commit、当前 commit/未提交差异、完成的工作包和停止位置。
2. 修改/新增文件，公共函数和输入输出契约，兼容性影响。
3. 验证命令、退出码、实际测试数、ignored/未运行项。
4. 真实操作证据：goal、graph、execution、产物、审批/取消、截图与日志关联。
5. 与其他工作线的接口变化及需要集成负责人接入的最小补丁。
6. 已知缺口、失败原因、下一项明确动作，不扩大原任务范围。

推荐 Conventional Commit 主题分别对应工作包，如 `feat(proofloop): compile capability-bound task plans`、`feat(proofloop): verify goal evidence`。提交前核对暂存文件与 diff；提交、推送和合并仍需任务已有授权，不能由本方案隐含触发。

- [ ] 三组评测可由原始数据复算；所有研发目标与实测值分开。
