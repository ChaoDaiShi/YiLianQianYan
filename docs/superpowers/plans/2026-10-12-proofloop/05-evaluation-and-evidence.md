# 评测任务集与比赛证据包

> 状态：PLANNED。负责人：F。任务集、基线和公共判定器从 I0 启动；真实数据随 G1/G2/G3 逐步采集。当前没有证行专项实测数字。

| 工作包 | 拟新增位置 | 产物 |
|---|---|---|
| F1 任务集与判定契约 | `backend/tests/fixtures/proofloop/benchmark-tasks.json` | 30 个固定任务、期望成果、必需条件、能力配置 |
| F2 原始记录和计算 | `scripts/proofloop/summarize.mjs`；`benchmark-manifest.json` | JSONL 记录、结果聚合、错误分类 |
| F3 真实产品驱动 | `frontend/e2e/proofloop.mjs`，集成负责人接 `core-paths.mjs` | 浏览器/API/窗口操作与真实 execution 对应 |

只新增能执行实际产品流程的薄脚本；不能通过检查文件存在、读历史日志或静态源码就输出业务 PASS。F 负责公共判定器的独立口径，C 提供结果结构但不能自己指定成功标签。

## 2. 三组主对照与一个恢复补充对照

| 组 | 配置 | 要回答的问题 |
|---|---|---|
| B0 当前方案 | 固定基线提交的既有自然语言规划、现有画布操作和手动能力/绑定配置 | 当前流程实际能完成多少，需多少人工操作 |
| B1 能力约束编译 | I1 编译器 + 同一工具/模型 + 原有执行；关闭目标驱动修复 | 自动编译本身是否提高可执行率、减少配置 |
| B2 完整证行 | I1 + I2 + I3，保持同一能力集和总预算 | 验收和有限修复是否提高最终完成率 |
| BR 固定重试 | 与 B2 相同的初始计划和工具，失败后原计划重试，最多两轮 | 修复改计划是否优于仅重试 |

B0 本来只选择工作流，不能人为给它增加未有的自动编译能力。它可使用当前产品已有手动配置能力，所有人工成本计入。对于超出现有自动规划能力的任务，保留“未生成可执行计划”结果；同时报告三组共同支持任务子集与全部目标任务集，避免范围差异被藏起来。

所有组使用同一独立目标判定器/rubric，B0/B1 也按同一条件检查成果。不能只有 B2 被严格验收，或让 B2 自己输出的 pass 直接充当实验真值。

使用固定资料快照保证可复现，同时另列实时联网子集验证实际应用。网络动态来源变化记录抓取时间；快照实验与联网实验分别汇总。

## 4. 故障与权限场景

在 T01/T05/T08/T10/P09 等适配任务上各自注入：工具不可用、输入类型不符、缺结构字段、服务超时、无效路径、图版本变化；另测授权拒绝、用户取消、预算耗尽和外部写入结果未知。

“可恢复故障”必须在运行前定义为：允许集合中存在兼容替代能力或已知合法输入修正，且不依赖新增权限。授权拒绝、用户取消、不可恢复缺能力、结果未知的外部写入属于正确停止场景，不纳入恢复成功率分母；仍全部进入异常场景报告，不能藏掉。

故障使用测试 MCP 服务、受控代理或测试输入注入，不修改生产工具结果。标记 `controlled_fixture`；实际业务 MCP 标记 `real_business_tool`。

## 5. 固定预算与运行次数

初始预算建议每任务：总模型调用最多 6 次、总 token 24,000、端到端 10 分钟、修复最多 2 轮；token 包括模型返回的可计费用量，供应商未提供的项目标 unknown，不能填 0。工具调用次数同时记录，上限按具体任务在运行前固定，各组相同。

时间上限用于实验终止，不保证第三方服务时延。模型名称、精确版本/供应商、温度、最大输出、提示词版本、工具 schema 摘要、网络环境和资料版本都记录。

总模型预算包含规划、候选语法修正、已有工作流/Agent 在实际节点内的模型调用、修复建议以及可选的模型解释，不只统计 ProofLoop 新增代码。模型未提供 token 用量时保留 unknown，并使用调用/耗时上限终止；不得把未知用量当作剩余预算无限继续。

每个任务每组至少 3 次有效启动，共 30×3×3=270 次主实验；BR 在故障子集另计。顺序交错运行，减少网络/时段偏差。任务开始后的失败、超时、取消均保留，不以“没有结果”删除。因实验环境未准备而从未启动的样本单列 BLOCKED，并报告实际启动覆盖率。

如果时间不足，只交 6 任务的真实试运行，不能将 18 次运行解释为完成 270 次实验。阈值是研发目标，未达标要报告实际值和失败类型；不要增加每组不同的隐藏重试预算。

## 6. 指标定义

| 指标 | 计算口径 | 研发目标/解释 |
|---|---|---|
| 初始计划可执行率 | 首次候选无需人工修改且确定性编译 ready 的启动次数 ÷ 全部规划启动次数 | ≥85%；无响应/非法 JSON/缺工具计未通过 |
| 人工确认后可执行率 | 经人工补充后 ready 次数 ÷ 全部规划启动次数 | 单列，不能与自动可执行率混用 |
| 目标完成率 | 独立判定器认定全部必需条件满足的次数 ÷ 全部任务启动次数 | B2 比 B0 提高 ≥15 个百分点；human_pending 未通过 |
| 可恢复故障成功率 | 预算内恢复且最终目标通过次数 ÷ 预先定义的可恢复故障启动次数 | 报告 B2 对 BR 的差异和原始计数 |
| 人工操作量 | 固定 rubric 记录点击、手动绑定、参数修改、审批、人工复核 | 配对任务中位数减少 ≥30%；配置与必要审批分别报告 |
| 非法真实执行 | 虚构能力、无效参数越过校验或未授权工具实际执行次数 | 0；同时报告阻止的非法提案数量 |
| 错误验收通过率 | 产品判 pass 但独立判定失败的次数 ÷ 产品判 pass 次数 | 目标 0；分母为 0 显示 N/A |
| 时间与消耗 | 总耗时、主动操作时间、等待时间、模型调用/token/工具调用数 | 各组报告中位数、P90 和未完成样本消耗 |

时间和成本既报成功任务，也报所有启动任务的消耗，避免只保留快成功样本。人工步骤使用同一操作规则和同一熟练度条件；同一人熟悉任务后会减少操作，运行顺序应交错。试用反馈需要真实参与者和记录，不将操作脚本次数写成用户研究。

30 个任务的小规模评测应优先报告原始计数、配对差异和不确定性。若报告置信区间，以 task ID 为聚类单位做配对重采样，不能把同一任务三次运行当成三个独立用户，也不在证据不足时使用“显著领先”。

## 7. 原始记录格式

每次运行一条 JSONL，并以 run_id 关联截图、日志和成果。以下为格式示例，不是实测结果。

```json
{
  "schema_version": 1,
  "run_id": "example-A01-B1-01",
  "task_id": "A01",
  "group": "B1",
  "commit": "record-at-runtime",
  "environment_kind": "controlled_fixture",
  "started": false,
  "status": "NOT_TESTED",
  "graph_id": null,
  "graph_revision": null,
  "goal_id": null,
  "goal_version": null,
  "execution_ids": [],
  "initial_compile_ready": null,
  "goal_pass": null,
  "human_operations": null,
  "model_calls": null,
  "tokens": null,
  "tool_calls": null,
  "repair_rounds": null,
  "elapsed_ms": null,
  "evidence_paths": [],
  "failure_code": null
}
```

真正执行记录必须写实际 commit，且 `started=true`；成本未知用 null 并说明原因。证据路径要存在且可以追踪到当前运行；缺证据不能仅凭 exit 0 写 PASS。脱敏令牌、请求头、用户隐私和完整敏感参数；不把凭据写入 JSONL、截图或仓库。

## 8. 证据包与比赛材料

每个候选提交生成一份清单：基线/候选提交、模型与工具版本、任务输入摘要、运行编号、原始记录、统计脚本版本、结果报告、已知限制、成果摘要、构建制品摘要。大体积原始输出留本地交付目录，仓库提交脱敏摘要和可复现脚本，不提交凭据或用户数据。

比赛材料按事实组织：

1. 用户场景与痛点：同一任务原流程/新流程的实际人工成本。
2. 算法说明：候选生成、能力约束编译、目标判定、修复补丁及边界。
3. 架构和数据流：标出复用模块与本轮增量，不把整个底座列成新发明。
4. 演示视频：从目标输入到真实成果，含一次失败、修复或正确停止，画面与记录关联。
5. 测试报告：三组原始计数、预算、失败样本、恢复对照与误报检查。
6. 使用/部署说明：真实可安装候选、依赖与模型配置方式、已知限制；不含明文密钥。

官方要求软件核心功能完整，并提供软件说明、演示、核心算法、测试及运行部署材料；本方案按这些交付类型收集证据，不预估评委分数。[官方赛题要求](https://www.aicomp.cn/tracks/tracks-2/3792.html)
