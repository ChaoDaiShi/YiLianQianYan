# I3 证据驱动的受控修复

> 状态：PLANNED。负责人：D。依赖 [I0 契约](00-contracts-and-ownership.md)、[I1 编译器](01-capability-and-compiler.md)和 [I2 验收](02-goal-acceptance.md)。纯提案和补丁校验可提前开发，真实应用必须等到 G1/G2 通过。

## 1. 目标与边界

将具体失败记录转为可解释的局部修改建议，在用户确认后复用既有 Harness 重跑受影响分支。首轮最多两轮修复；每轮都保留提案、修改前后差异、新 execution IDs 和新验收报告。

修复不改变最初目标的必需验收条件，不抬高预算，不增加 capability 允许范围，不创建永久授权，不清除失败历史，不自动改动无关的成功分支。新修复提案不绕过现有 High 风险 MCP 审批。

## 3. 失败分类与允许动作

| 已观察到的失败 | 首轮允许的建议 | 必须停止或等待的情形 |
|---|---|---|
| 固定输入字段错误 | 替换该字段为已确认的合法值 | 缺少真实值且用户未提供 |
| 绑定路径缺失/类型不符 | 换用声明或已确认真实输出中的兼容字段 | 没有兼容来源，禁止隐式转换或编造字段 |
| 工具不可用 | 选择允许范围内、当前 Ready、输入输出兼容的能力 | 需要新增能力、安装工具、增加资源授权 |
| 已确认无副作用的失败调用 | 建议原参数重跑 | 远端副作用状态未知 |
| 目标验收缺章节/缺成果 | 修改产生该成果节点的合法输入，再局部重跑 | 需要更改用户原始验收标准才可通过 |
| 审批拒绝/授权不足 | 展示原因，交还用户 | 不自动再申请或用其他工具规避拒绝 |
| 取消 | 停止当前修复与后续调度 | 不自动继续 |
| 网络超时、写入结果不明 | 先显示“结果未知，需核实” | 不能仅凭超时判定未执行并自动重做 |

MCP 工具声明的 idempotent/readOnly annotation 不能单独作为自动重试授权。首轮用户确认修复后仍走已有审批；对于结果未知的外部写入，只能使用既有查询能力核实或交用户处理，不引入事务平台或补偿引擎。

## 4. 修复补丁验证

1. 读取目标 version、源报告、失败 execution 和当前图 revision；任一不匹配则提案 stale。
2. 只允许 I0 的四种操作：replace_literal、replace_binding、replace_capability、rerun_node。
3. 校验每个修改节点属于失败根节点的受影响分支，且存在真实失败/验收缺口理由。不能修改另一条成功分支。
4. 替换能力后重新核对 allowed 集合、Ready 状态、input/output schema、绑定以及交付物覆盖。
5. 将补丁应用到内存候选图，调用 B 的编译检查与既有图/绑定校验；不能逐条写 DB 后再发现后续操作不合法。
6. 由既有 affected_branch 规则计算受影响后代；不接受模型自己给出的 affected_node_ids。
7. 计算用户可读差异：修改节点、参数来源、能力变化、需要重新审批的操作、将失效的下游结果。
8. 用户确认的是这一版提案；图变化后需重新展示，不将旧确认应用到新 revision。

每次提案只选一个 rerun_root_node_id。多处分离失败按不同轮次处理，受总预算约束；不为了首轮引入复杂补丁事务语言。

### 关键应用顺序

```text
用户确认 repair_id + expected_graph_revision
  → 检查取消、总预算、提案未重复应用
  → 在既有图修改锁下读取当前版本和活动执行
  → validate_repair 得到候选图和影响范围
  → 原子保存图修改、修复应用结果与重跑准备状态
  → 更新 runtime 内存
  → 交给现有调度/执行入口
  → 新 attempt 重新经过参数解析、Gateway 和审批
  → 收集新证据，重新 evaluate_goal
```

拟新增 `apply_repair` 只做上述协调。`prepare_rerun_from_node`、实际调度和取消机制继续复用；如现有事务入口不能承载最小原子操作，由集成负责人补一个面向本操作的入口，不新建第二套 runtime。

## 5. 重跑与成功节点的精确定义

现有 `rerun_from_node` 会让受影响分支的旧 attempt 变为 stale，并保留历史。原报告“不修改已成功节点”应解释为：不改无关成功分支的定义和执行；被修复节点的下游即使此前成功，也必须失效并重新验证，不能继续将旧输出作为当前成果。

现有 U3.1 允许特定 WaitingApproval 后代保留冻结参数。**I3 补丁应用不利用这一例外改变待审批计划。** 如果修复影响的节点存在 running/WaitingApproval，先要求通过原入口取消或等待结束，再重新检查。这样不改动已展示审批的参数，也不削弱已有普通重跑行为。

同一 repair_id 重复 apply 返回已应用的 revision，不重复排队；应用后程序退出，沿用既有 interrupted/recovery 行为，修复预算与已应用记录仍可读取。

## 6. 预算与终止规则

默认 `max_repair_rounds=2`，且总模型调用、token、耗时均受 GoalContract budget 限制。轮次在接收一轮新的修复提案请求时由服务器预留并持久化，模型失败/无效提案也占该轮；重新读取已有提案不占新轮。同一确认重发不计新轮也不执行第二次。

普通节点重试和修复重跑不能叠加成隐形无限重试：评测统一累计全部 attempt、tool call 和模型调用；首轮图的自动 retry_policy 默认 1，必要的固定重试只在明确的对照实验中配置。

任一条件成立即停止：用户取消、授权拒绝、预算耗尽、连续同一补丁未改善、无法获得兼容能力、外部写入结果未知、图版本变化未重新确认。前端展示具体原因和当前成果，不使用“正在努力”掩盖循环。

## 7. 行为测试与 G3

| 编号 | 场景 | 预期 |
|---|---|---|
| R01 | 失败 B，成功无关分支 C | 只修复 B 及依赖后代；C 的执行计数不增加 |
| R02 | B 的下游 D 之前成功 | D 旧结果 stale，新 attempt 后再验收 |
| R03 | schema 兼容替换 | 再编译成功；新能力重新走 Gateway/审批 |
| R04 | 替换到不允许能力/修改验收标准 | 提案拒绝，图不变 |
| R05 | 旧图版本提案 | 409/stale，原图和运行状态不变 |
| R06 | 影响分支正在执行或待审批 | 拒绝应用；既有审批参数不变化 |
| R07 | 重复确认、重启后再读提案 | 至多一次应用，新旧历史可追踪 |
| R08 | 超过两轮、模型错误、重复无效修复 | 消耗与终止原因真实记录，无无限请求 |
| R09 | 外部写入超时，结果未知 | 不自动重试写入 |
| R10 | 原审批拒绝/用户取消 | 后续模型与工具调用不继续 |
| R11 | DB 写失败或应用半途错误 | 不留下“提案 applied 但图未改”的假状态 |

G3 至少运行一条“缺字段→合法修复→重新验收通过”的真实链路和一条“不可修复→明确停止”的链路，保存首次失败、提案差异、确认、Gateway/审批、新 attempt 与最终验收记录。
