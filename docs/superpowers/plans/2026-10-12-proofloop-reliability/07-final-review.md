# G 独立终审与修复交接

> 执行方式：按本页检查实际代码与证据。状态：PLANNED。终审由非本轮主要实现者完成；当前计划编写与自检不称作独立终审。

**目标：** 对六类修复、产品接线、真实实验和比赛表述作最终判断，阻止“局部测试通过”被扩大为完整专项验收。

**架构与技术范围：** 只审查本轮 Rust/React/Tauri/SQLite 变更及其真实依赖，沿用现有安全网关和独立私有服务器边界。

## 1. 审查前必须拿到的材料

- 候选完整提交 SHA、合并基线、改动文件清单、各工作包负责人。
- A—E 的负例、正例、实际退出码、测试数量与运行版本。
- 受控产品流程和真实业务流程各自的请求、执行、产物和页面证据。
- 270 次实验原始记录、任务/工具/模型版本、独立判定器、统计脚本和失败列表；不足时列出真实数量。
- Windows 候选安装包、SHA256、实际运行版本、桌面与两设备记录。
- 旧数据兼容、未测项目、供应商未知用量、保留的警告和未达到的研究目标。

## 2. 问题到证据的终审矩阵

| 问题 | 审查代码路径 | 必须复核的证据 | 拒收条件 |
|---|---|---|---|
| R01/R01a | recover、proposal、旧 apply、retry、rerun、scheduler | A01 外部计数；A03 旧提案；A04 旧 policy；A05 分支原子拒绝 | 任一入口可使未知调用再次发出 |
| R02/R02a | 创建/CAS、确认成功事务、确认失败回写 | B01—B07 的固定交错与重开结果 | 旧请求覆盖 confirmed、同版丢更新、事务半提交 |
| R03 | 基础成果结果、人工复核和总状态 | C01 缺成果人工 pass；C02 多交付物；实际 HTTP/刷新 | 无必需成果却显示 Pass |
| R04 | 规划计时、dispatch、审批恢复、修复预算事务 | D01/D02 长等待；D03 并行；D05 双入口；D07 重启 | 人工等待误扣、重跑清零、未知历史伪造为 0 |
| R05 | 精确 SQL 与 provenance/file 检查 | C06 超过 200 条无关记录；C03 跨图同名；C07 最新版本 | 只是提高 limit，或回退旧文件冒充成果 |
| R06 | records、三态请求、实际 UI 与原冲突事务 | E01 真实参数；E02 副本；E03 幂等；E10 两设备 | 副本仍映射 local、固定代次/版本、上传状态冒报 |
| R07 | 实验驱动与独立判定器 | run 到 actual execution/file 的逐条关联 | 静态文件检查代替业务运行、删除失败样本、产品自评作真值 |

审查不能只看修复分支：必须检查实际候选合并树。R01 发现同源调度路径，因此终审也应沿错误码的消费者追踪，不能只确认 repair.rs 的字符串已删除。

## 3. 复核顺序

1. 确认候选源码和运行制品一致，检查是否有未提交或未纳入构建的代码。
2. 先复核 A 的未知副作用场景，再运行其他外部工具场景。
3. 复核 B 的真实数据库交错，不接受“连续两个旧请求”替代并发交错。
4. 复核 C 的缺成果负例和大量历史记录正例，检查 UI 与独立判定是否一致。
5. 复核 D 的每个预算入口、旧数据状态及真实取消；时间测试使用可控时钟，外部取消另有真实调用证据。
6. 复核 E 的副本 ID、原对象、outbox 和两设备状态；已有云后端能力不等于本轮 UI 已接通。
7. 随机抽取至少每类任务、每组、每重复号各有覆盖的样本复算；对全部失败/误报/非法执行记录逐条检查。
8. 阅读比赛介绍、演示和统计结论，确认没有把规则恢复写成复杂自主推理、把未测写成通过。

审查人发现问题后回到所属工作包小范围修复，重跑受影响的证据。若候选代码变化，旧制品与旧实验仍保留但不能冒充新 SHA 的运行；由变化影响范围决定需要重跑的样本并说明依据。

## 4. 状态与结论规则

| 结论 | 条件 |
|---|---|
| `NEEDS_FIX` | R01—R06 仍有可复现缺陷，或证据显示越权/重复外部执行/错误 Pass |
| `FIXES_VERIFIED` | 新增负例、保留行为及必要产品接线通过；仅说明代码修复范围 |
| `ACCEPTANCE_INCOMPLETE` | 缺外部业务、实验覆盖、真实桌面、两设备或独立终审任一必要证据 |
| `PROOFLOOP_SCOPE_ACCEPTED` | 总计划 G1—G5 全部有当前候选的证据，且独立审查未发现阻断问题 |

工程验收与研究收益分开写。实验完整但提升未达到目标时，报告“实验完成、指标未达标”及实际差值，不能写“创新收益达标”；也不能把性能未达标伪装成某个样本未启动。

若独立人员不可用，状态写 HUMAN_PENDING，整体保留 ACCEPTANCE_INCOMPLETE。不得由实现者换一个角色名后填写“独立终审通过”。

## 5. 最终交接记录字段

最终报告至少包含下面的字段和值域，实施时填写真实结果，不复制本计划中的 PLANNED 为 PASS：

| 字段 | 内容 |
|---|---|
| candidate_commit / artifact_sha256 | 完整源码 SHA 与实际安装包摘要 |
| review_baseline | 本轮比较基线及后续集成变化 |
| fixed_findings | R01—R06 对应的修复提交与用例 |
| engineering_status | NEEDS_FIX 或 FIXES_VERIFIED |
| acceptance_status | ACCEPTANCE_INCOMPLETE 或 PROOFLOOP_SCOPE_ACCEPTED |
| evidence_coverage | 单元/集成、受控、外部业务、桌面、两设备、实验分别标记 |
| benchmark | 主实验计划数/实际启动数、BR 数量、失败数、误报数、实际指标 |
| innovation_result | 有数据且达标、有数据但未达标、无足够数据三者之一 |
| reviewer | 实际独立审查人的身份与日期；未完成写 HUMAN_PENDING |
| unresolved_items | 问题、影响、已有证据、责任工作包和下一步 |

建议本轮实际结果另存 `docs/superpowers/plans/2026-10-12-proofloop-reliability/08-implementation-review.md`，旧的 `2026-10-12-proofloop/07-final-review-report.md` 保持历史证据；总计划可链接新报告并更新完成状态，不覆盖历史结果或清除失败记录。
