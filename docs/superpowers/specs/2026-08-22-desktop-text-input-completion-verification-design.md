# 桌面文本输入完成验证设计

**日期**：2026-08-22
**状态**：已批准（用户已授权本轮自主修复）
**范围**：修复“打开记事本并输入文本”只完成启动应用却被报告为成功的问题。

## 1. 问题与根因

当前 `open_application` 已能验证目标窗口可见并位于前台，但 ReAct 循环在模型返回普通文本且不再调用工具时，会直接发送 `done`。系统提示词没有列出 `keyboard`，也没有要求桌面多步骤任务必须逐项获得可观察的成功证据。因此，模型可能在记事本启动后直接回答“已完成”，而实际没有发生文本输入。

现有 `keyboard` 的 `type` 操作还会向当前未知焦点窗口注入按键。即使调用成功，也只能证明系统接受了输入事件，不能证明事件发往了用户要求的应用。

## 2. 方案

采用“目标受限输入 + 任务完成证据门”的最小增量方案：

1. `keyboard(action=type)` 必须携带 `target_application`。
2. 安全描述符把目标应用纳入桌面授权资源，审批内容明确展示输入目标。
3. 工具执行前确认并聚焦匹配的应用窗口；输入后再次确认该窗口仍位于前台。
4. 成功结果写入稳定、机器可判定的验证标记，但不回显用户输入全文。
5. ReAct 循环在桌面文本输入任务准备结束时，检查最新用户请求之后是否存在真实、成功且目标已验证的 `keyboard(type)` 调用结果。
6. 缺少证据时不发送 `done`，向模型提供简短的系统反馈并继续规划；连续两次仍无证据时明确失败，禁止误报成功。

该方案不会读取或展示模型私有推理，也不会伪造进度或工具状态。

## 3. 完成证据边界

完成证据门只针对明确的桌面文本输入请求，例如：

- “打开记事本，在新页面写入你好世界”
- “launch Notepad and type hello”

普通文件写入、代码编辑、聊天回复不触发该门，以免把 `write_file` 等结构化操作错误地要求为键盘输入。

判定只查看最新一条用户消息之后的工具调用及结果，旧任务中的键盘调用不能满足当前任务。

## 4. 数据流

```text
用户请求打开应用并输入文本
  → open_application（窗口可见/前台验证）
  → keyboard(type, text, target_application)
  → 安全网关按目标应用授权
  → 工具确认目标窗口并输入
  → 工具再次确认目标仍在前台并返回验证标记
  → 模型给出最终回答
  → 完成证据门检查最新请求的真实工具记录
     ├─ 有证据：发送 done
     └─ 无证据：继续规划；达到上限后发送 error
```

## 5. 安全与隐私

- 键盘工具保持高风险桌面交互审批，不降低现有风险等级。
- `type` 的授权从泛化桌面输入收紧为指定应用窗口。
- 目标窗口无法确认时 fail closed，不向未知窗口注入文本。
- 工具结果不回显输入全文，避免密码或敏感内容进入历史记录与日志。
- 不修改 SSE 事件语义、API Schema、数据库结构或审批后端语义。

## 6. 失败行为

- 缺少 `target_application`：工具拒绝执行并给出可理解错误。
- 目标窗口无法确认：工具拒绝输入。
- 输入事件失败：返回真实错误。
- 输入后目标窗口不再处于前台：结果视为未验证，Agent 重新规划。
- 模型两次尝试结束但仍没有真实输入证据：任务以“无法确认文本已写入目标窗口，任务未完成”失败，不发送 `done`。

## 7. 测试

- 系统提示词包含键盘工具及桌面多步骤完成规则。
- 安全描述符要求 `keyboard(type)` 提供目标应用并生成精确桌面资源。
- 键盘工具在目标未授权或窗口未确认时不注入；目标确认时只注入一次并返回验证标记。
- 完成证据门覆盖：只打开应用、成功输入、失败输入、旧历史证据、普通文件写入。
- 运行 backend 全量测试、`cargo fmt --check`、`cargo check`，并运行 frontend 测试与生产构建确认 SSE/UI 回归。

## 8. 非目标

- 不实现完整 Windows UI Automation 文本内容读取。
- 不对任意 GUI 操作建立通用任务规划器。
- 不修改模型 Prompt 之外的模型能力或新增推理步骤。
- 不修改 frontend 的 Agent 状态模型。
