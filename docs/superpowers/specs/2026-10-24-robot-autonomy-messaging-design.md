# 连接应用的机器人自主能力与消息工作台设计

状态：待用户审阅。本文件描述拟实施行为，不代表功能已经落地。

## 1. 已保存的版本

用户要求先合并当前版本，再扩展机器人自由度。本地 `develop` 已快进至 `b08c848c8c7a254d495144e6002e87d933237364`，标签为 `baseline/v1-r3-before-robot-autonomy`。源码基线范围与验证结果见 `docs/releases/v1-r3-before-robot-autonomy.md`。

后续工作分支为 `codex/robot-autonomy-messaging`。本轮未推送远端，也未修改 `main`。

## 2. 用户目标与本轮边界

用户希望机器人能主动了解 QQ 中的好友、群和会话，围绕目标操作 QQ；外部消息页改为左侧导航与顶部操作，使会话内容获得主要空间；另外调查并补充可用的 OneBot 微信接入。

本设计拆为两个可独立验收的实施单元：

1. QQ 自主操作与消息工作台：QQ 的探索、读消息、主动发消息、主人指令、任务调度与活动记录，以及各平台共用的新布局。
2. 额外微信接入：先确定用户所指项目，再按实际协议和能力矩阵实施与验收。该单元不阻塞 QQ 与布局。

沿用 Rust / Axum / Tokio / SQLite / Tauri 与 React / TypeScript；复用现有 Agent、工具网关、会话、取消与 Automation / Workflow。此次不设计新的 Agent 核心或另一套调度器。

## 3. 方案比较

| 方案 | 行为 | 取舍 |
| --- | --- | --- |
| 推荐：结构化 QQ 工具 + 目标任务 + 授权范围 | Agent 查询真实好友、群、最近会话、历史；自己决定下一步并调用 QQ API；可自动向已授权目标发言 | 复用现有 NapCat 与 Agent；可观察动作和回执；需要增加 QQ 工具、任务身份和授权描述 |
| 仅扩大监听名单 | 更多好友或群收到消息时才回复 | 改动较小，但无法满足主动探索与目标驱动操作 |
| 以桌面鼠标键盘作为 QQ 主控制方式 | Agent 操作 QQ 窗口完成读写 | 依赖窗口状态，现有 OneBot API 已覆盖主要操作，不作为本轮主实现 |

采用推荐方案。QQ API 明确返回不支持时，界面显示具体能力不可用，不暗中切换 UI 自动化或其他协议。

## 4. 主人、普通联系人与目标任务

### 4.1 主人指令

在每个 QQ 渠道的“机器人”设置中保存主人 QQ 号。主人可从桌面输入目标，也可在 QQ 私聊给机器人下达目标，例如“看看最近有哪些会话，读一下某个群最近的讨论，再给我总结”。

主人身份由已验证渠道的发送者 ID 判断，不能由消息正文声明。普通联系人仍可以正常聊天；其正文、引用、群历史都作为会话内容，不能改写主人的目标或渠道授权。

启用自主模式后，主人的一条指令启动正常 Agent 多步执行，拥有该账号被授权的 QQ 工具。普通联系人触发的聊天只拥有当前私聊／当前群的阅读与回复范围。群成员发言不自动成为跨会话控制命令。

### 4.2 目标任务

桌面端“机器人”页提供目标输入、开始、停止、运行详情。示例目标包括查看近期会话、查阅指定群讨论并总结、向选定联系人主动问候或跟进消息。任务中的目标和模型／角色预设均可保存。

任务状态为排队、运行、等待审阅、已完成、已停止、失败。步骤显示实际工具、目标联系人／群、返回摘要以及发信回执。正在运行时可停止，停止后不得启动下一条工具动作；已经交给平台的消息保留其平台回执或送达未知结果。

可选择立即执行，也可绑定现有 Automation 支持的一次、每日、每周计划。周期任务调用同一套 QQ 工具与权限；沿用当前调度器不补跑错过时段的行为。不能在模型输出中宣称已创建计划而不实际保存 Automation。

当前 Automation 只执行 WorkflowGraph，且现有 Workflow Agent 节点是单次无工具文本生成，不能直接用于多步 QQ 操作。因此拟给 Automation 增加显式 `AgentTurn` 执行目标，关联已保存的机器人目标任务；触发时调用已有 ChatRuntime 与 ReAct engine。旧 Workflow 目标与原 Agent 节点语义保留。不会把保存一个文本节点当成已实现自主任务。

## 5. QQ 首批能力

以下为拟新增工具能力，底层使用现有 OneBot 11 HTTP／反向 WebSocket 连接。界面展示服务实际返回的资料。

| 能力 | 平台动作 | 产品呈现 |
| --- | --- | --- |
| 账号信息 | `get_login_info` | 显示当前操作账号，避免渠道与账号混淆 |
| 查找好友 | `get_friend_list` | 好友列表、名称与 ID 搜索、选择发信对象 |
| 查找群 | `get_group_list`、`get_group_info` | 群列表、基本信息、选择群 |
| 查看群成员 | `get_group_member_list` | 指定群成员资料，供目标任务查阅 |
| 最近会话 | `get_recent_contact` | 最近联系人／群，不把本地收信日志伪装成完整远端会话 |
| 私聊历史 | `get_friend_msg_history` | 指定对象、明确条数／分页，展示返回的历史 |
| 群历史 | `get_group_msg_history` | 指定群、明确条数／分页 |
| 查询单条消息 | `get_msg` | 查看已知消息 ID 的真实正文 |
| 主动私聊 | `send_private_msg` | 不要求对方先发一条消息；记录目标、正文和平台 message_id |
| 主动群聊 | `send_group_msg` | 可主动参与已授权群；记录群目标、正文和平台 message_id |

最近会话和历史查询包含 NapCat 扩展，不能向所有 OneBot 11 实现承诺可用。连接检查分别报告基础连接与这些操作的实际支持状态。失败时保留平台错误，不能返回编造的联系人、历史或成功记录。

本轮主要交付文本会话和结构化 QQ 控制。文件、图片、语音及账户／群管理动作需要各自的资源处理与授权，不能仅因 NapCat 文档列出了接口就标记为已支持。

## 6. 授权如何体现自由度

用户在本机一次选择读取范围和发送范围，范围内的正常工具执行不逐条弹窗。支持“指定好友／群”与“全部好友／群”两种范围；用户可分别设置私聊和群聊。界面直接写明当前生效账号与对象范围。

读取范围与发送范围分开保存。用户可允许探索所有好友、群和会话，而仅允许向选定对象自动发言；也可主动选择向全部好友／群发言。普通聊天与主人的目标任务分开判断执行身份。

如果用户选择逐条审阅，继续使用现有审批流程。若发送目标超出当前自动授权，显示该目标的授权／审阅需求，不自行扩大范围。已经授权的自动回复保持自动，不因增加目标任务而回到每条批准。

待用户决定的范围问题：默认采用指定目标自动发言、全部目标自动发言，还是逐条审阅。该选择尚未收到回答；不能用等待时长代替授权。

实现上扩展现有消息权限与资源描述，使账号、目标类型、目标 ID、读／写动作成为网关可检查的数据。不能只给模型一段提示词，同时保留任意 QQ 发信通道。已有本机文件、进程、Shell 等工具不会因为收到一条 QQ 消息而自动对普通联系人开放。

## 7. 与现有消息链路衔接

目前 `backend/src/modules/channel/mod.rs::restrict_runtime` 对渠道会话清空工具；`receive` 只接允许名单的私聊文本；`onebot_ws.rs::Session` 只公开私聊发送。这里需要增量扩展，不复制新连接器。

1. 将 HTTP 与反向 WebSocket 的 QQ API 调用封装成有明确动作、参数与 echo 回执的统一调用入口，继续沿用当前认证与连接状态。
2. 入站事件保留 peer 类型与 ID。私聊和群使用不同会话键；群的接入范围与成员 ID 分开判断，不能用允许发信人的私聊名单代表群授权。
3. 根据入口身份选择 QQ 工具范围：桌面主人目标、QQ 主人目标、普通会话。连接凭据留在服务端，不进入模型工具结果。
4. 自主任务的对外消息通过工具发送，并写入活动记录；任务最终总结显示在任务详情中。若需要向 QQ 主人报告，明确执行一次向主人回复。
5. 每个入站回合明确采用“生成回复交给既有发送链路”或“由工具发送”之一。已由工具回复当前回合时，不再由 `send_if_automatic` 追加发送同一正文。执行身份、回合和发送记录共同决定发送状态，不能靠比对字符串判断重复。
6. 保留现有取消、迭代限制、去重与送达未知处理。平台可能已受理但本机未收到回执时，不自动重发写动作。

本地保存 QQ 策略、目标任务与动作回执；现有渠道配置和历史会话保留。新增字段及迁移遵循当前 SQLite 数据管理方式，不覆盖运行库或清空旧记录。

### 7.1 拟新增数据与执行接缝

- QQ 策略保存渠道与账号、主人 ID 列表、可读对象范围、自动发送对象范围和群触发方式。群触发可选提及机器人或全部消息；普通群消息仍只有当前群会话权限。
- 入站消息、会话与消息记录增加明确的 `peer_type` 和 `peer_id`；现有私聊记录迁移为 private，群会话按 channel + group + group_id 区分。发言人的 `sender_id` 单独保留。
- 机器人目标任务保存渠道、目标正文、预设与版本；运行记录保存本次目标快照、入口身份、会话／轮次 ID、实际状态。授权范围使用当前已保存策略，变更后影响后续动作。
- Automation 的执行目标明确区分 `Workflow` 与 `AgentTurn`。旧记录迁移为 Workflow，不推测目标类型。AgentTurn 关联机器人目标任务，继续用现有时区计算、occurrence 去重与调度器；本次 occurrence 关联真实 Agent run / conversation / turn，不能填造 Workflow run_id。
- 目标运行服务负责组装 ChatRuntime、给出 QQ 工具和 scoped execution context、转发取消与结果持久化。桌面立即执行、QQ 主人指令与定时触发都进入同一服务；不各造一套 Agent loop。
- 活动记录至少保存运行／轮次、工具动作、账号、目标类型与 ID、平台 message_id 或错误／送达未知。读取结果和写入回执分别呈现。

以上名称是拟新增契约；实施计划需先冻结具体 Rust / TypeScript DTO 和 API，再并行分配工具、调度和界面任务。保留现有 API 路径，前后端同步更新明确的执行目标字段。

## 8. 消息工作台布局

采用一条左侧导航、中央会话区和顶部操作栏。保留应用原有导航，不再把三个大接入说明卡片放在消息页顶部，也不固定占用右侧配置栏。

```text
┌──────────────────────────────────────────────────────────────────┐
│ 消息  · 当前应用／账号        连接状态   机器人  预设  设置  添加 │
├─────────────────┬────────────────────────────────────────────────┤
│ 应用与账号       │ 当前会话／任务标题                对象信息     │
│ QQ / 微信 / 飞书 │                                                │
│                 │ 实际消息、草稿、自动回复与发送回执              │
│ 会话 / 通讯录   │ 或：好友、群、目标任务与执行步骤                │
│ / 机器人活动    │                                                │
│                 │                                                │
│ 搜索与对象列表   │ 当前对象输入框／目标任务输入                    │
└─────────────────┴────────────────────────────────────────────────┘
```

### 8.1 左侧

上半区为平台与账号，显示小尺寸状态标记；下半区显示所选账号的会话、通讯录或机器人活动。QQ 的通讯录包括好友和群，可以搜索并打开对象；从对象详情可阅读历史或主动发消息。其他平台仅呈现已实现的能力。

会话列表的预览、时间和计数必须来自实际消息。现有会话 DTO 没有未读字段，因此不生成假未读数。QQ 远端历史与本应用记录有明确来源，不混成一份声称完整的聊天记录。

### 8.2 顶部与中央

顶部集中放连接状态、当前回复／自主模式、机器人、预设、刷新、添加与设置。中央优先展示消息与任务内容；入站消息、生成回复和发送状态按会话呈现，保留编辑草稿、审阅、停止与失败说明。

回复模式控制实际持久化策略；不能只是切换按钮外观。主动发送使用真实的目标选择与发送接口，不能借用旧消息的回复按钮假装向任意联系人发信。

### 8.3 配置抽屉

接入配置、连接检查、登录二维码、主人与操作范围、平台说明放入现有 Drawer。未保存的预设继续走现有离开提示。没有账号时显示简洁的接入引导；说明按需展开。

1440 宽窗口左栏约 280–320 像素；1200 宽约 240–270 像素。小于 960 像素折叠导航为选择器／列表与详情切换；小于 760 像素抽屉占满可用宽度。沿用当前昔涟主题、字体、背景、图标与 CSS 变量。

## 10. OneBot 微信方案的判断

用户所指具体项目仍待提供名称／链接，或明确由本轮选择。不同方案分别实施，不将 OneBot 11 和 12 混用。

- OneBot 生态列出的 ComWeChatBotClient 使用 OneBot 12、旧版 Windows 微信与 COM／Hook，项目已归档。此次不自动安装旧微信、替换现有微信或执行 COM 注册。
- OneBots 的微信 ClawBot 适配器通过 iLink 提供 OneBot 网关，可作为另一种接入路径研究；它与现有直连 iLink 部分重合，不能据此承诺任意微信好友／群和历史控制。
- 若选定 OneBot 12 方案，新增明确的 provider、平台与字符串账号／目标 ID，不套用 QQ OneBot 11 的数值 ID、私聊动作和群语义。按具体实现支持的动作开展接入检查、收发与登录验收。

微信子项目的完成标准是实际服务连接、登录状态、入站消息、明确回执的出站消息与手机端收件；单有模板或协议说明不足以通过。若选定方案存在登录前提，先向用户列出实际前提，不宣称所有个人微信账号均可直接接入。

## 11. 验收标准

1. 基线标签、develop 提交与版本记录一致，后续开发不改变该标签。
2. Agent 实际调用 QQ 好友、群、最近会话和历史 API；输出可追溯到返回资料，受控协议测试与真实账号验收分别记录。
3. 从桌面目标和已配置 QQ 主人各发起一次多步目标，完成探索、选择目标和发送；普通联系人不能取得跨会话控制身份。
4. 自动授权范围内发信无需逐条批准；超范围、被撤销范围和审阅模式按实际配置执行。界面可修改范围且即时影响后续动作。
5. 主动私聊与群聊各验证一次平台回执，并由对应收件端确认；真实发信前使用用户明确选择的测试对象。
6. 工具回复与既有自动回复不重复发送。断线、失败与送达未知分别记录，停止后不执行下一步。
7. 一次／周期目标通过显式 AgentTurn 目标绑定现有 Automation，实际运行带 QQ 工具的 ReAct，并能查看运行和停止；原 Workflow Agent 节点仍只生成一次文本，无后台重复调度器。
8. 新消息布局在常用桌面宽度与窄窗口可操作，配置不挤占常驻消息区，草稿与预设编辑不会在切换时无声丢失。
9. 后端格式、编译、相关权限／工具／渠道／调度测试与前端生产构建通过；最终在本机桌面端进行实际交互验收。
10. 微信与 Figma 分别记录其真实进展；未完成真实接入或插件写入时，明确标为未完成。
