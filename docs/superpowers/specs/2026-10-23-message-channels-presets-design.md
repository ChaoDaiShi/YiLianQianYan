# 消息渠道与回复预设设计

日期：2026-10-23（Asia/Shanghai）

状态：用户已确认本设计，功能已实施并进入真实微信账号验收。下文保留设计时的范围和拟定契约；实际验证结果见 `artifacts/message-channels-implementation/`，设计描述不能代替真实平台收发证据。

最新需求变更：用户在完成真实微信收发后明确要求自动回复。渠道现增加“自动回复 / 审阅后发送”选择；自动模式下新入站消息由模型生成后直接发送，不写入虚假的用户批准时间。下文早期设计中的“逐条批准”要求仅适用于人工模式。已有待审阅草稿不会因切换方式自动外发。

## 已核实的现状

1. `backend/src/api/channels.rs` 已注册渠道列表、创建、编辑、启停、消息与会话查询、逐条批准发送。管理接口受 control session 保护，平台回调走公开的协议认证入口。
2. `backend/src/modules/channel/protocol.rs` 已实现飞书未加密 HTTP 事件回调和 OneBot 11 HTTP 反向上报；OneBot 校验原始请求体的 HMAC-SHA1。
3. 飞书当前依赖可访问的 HTTPS 回调，而默认后台只监听本机地址。保存配置无法解决公网可达性问题。
4. `wechat_ilink` 当前在 provider catalog 中标为不支持；扫码凭据、轮询游标、会话 context token 均未实现。
5. 入站私聊文本按渠道和联系人建立本地会话，调用现有聊天运行时生成草稿，用户批准后再调用平台发送 API。
6. 外部渠道会话当前清空本机工具、能力、记忆和知识绑定。该现有行为应保留。
7. 现有字段没有回复预设、角色或模型档案引用，运行时还会整体覆盖系统提示词，不能只在表单中加入角色选项。
8. 当前 UI 缺少渠道删除、连接检查、预设管理和实时消息刷新；错误请求结束后可能误显示空状态。
9. 入站持久化和启动生成之间存在两段操作：记录已写入但渠道状态更新失败时，后续重复事件不会重新启动生成。实现时须修正这条实际业务路径。

## 方案选择

推荐在现有 Rust/Axum/Tokio 后端中增加渠道生命周期管理，沿用 React/Tauri、SQLite、SecretStore、ChatRuntime 和已有审阅外发流程。

另两种接法是：继续以 HTTP 回调作为全部渠道的主要方式，或者增加 Node 伴随进程运行参考项目 SDK。前者需要用户额外部署公网 HTTPS 入口，后者增加第二套运行时、配置和打包生命周期。推荐方案由 Rust 管理各平台的正式协议；已有 HTTP 接入可明确选择和继续使用，不作为失败时自动切换的备用方式。

## 交付行为

### 渠道接入模板

- 飞书自建应用：App ID、App Secret、允许联系人、回复预设。主要提供官方长连接接入，使桌面端无需公网回调即可接收事件。已有 HTTP 事件订阅配置仍按用户明确选择使用。
- QQ / OneBot 11：提供明确的 HTTP 与反向 WebSocket 接入方式，用户选择实际服务配置。提供可复制的接收地址、端口和鉴权说明；QQ 账号登录由用户的 OneBot/NapCat 服务完成。
- 微信 / iLink：请求官方登录二维码，展示待扫码、待手机确认、过期、已登录及服务返回的其他必要登录状态；支持取消和重新扫码。确认后写入本机凭据库，并保存 bot ID、平台返回的基础 URL 等非秘密元数据。
- 三种模板均不预填真实用户 ID、账号或凭据。保存、启用、账号校验、运行连接和收到真实消息分别表达。

### 回复预设

提供“昔涟 · 温柔日常”“简洁工作助手”“学习答疑”三种可复制的内置回复模板，并允许用户创建、编辑、复制和删除自定义预设。

回复预设拟包含：`id`、`name`、`agent_id`、`model_profile_id`、`instructions` 和创建/更新时间。角色和模型引用现有智能体、AgentProfile 和模型档案，不复制独立的模型凭据体系或完整 AgentDefinition。未选择角色/模型时明确采用现有默认聊天配置。

每个渠道选择一个回复预设。修改渠道预设作用于随后开始生成的入站消息；已经生成的草稿保留原文，除非用户明确重新生成。待发送消息不得因预设变化自动改写或重发。

预设试用通过真实配置的模型生成本地结果，不向外部渠道发送。展示使用的角色、模型和生成错误。模板只能控制角色与表达，不能扩大当前外部会话的工具、文件、记忆或知识权限。

### 收信、草稿和发送

首轮交付的统一协议范围为名单内私聊文本，与现有消息模型一致。接收不支持的消息类型时给出清楚的事件结果，不将其伪装为已成功处理的文本。若用户希望图片、文件、语音、群聊或无人审阅自动发送，需要确认扩展的具体范围后加入设计，不能从“参考项目”推定全部功能均获要求。

入站事件依次执行平台身份校验、允许联系人检查、持久化去重、关联会话、按预设生成草稿。记录接收和入队应保持同一业务提交边界，避免已去重但永不生成的消息。

收件箱会在页面可见时更新，并支持手动刷新。展示联系人、内容、时间、生成状态、使用预设、草稿和最近错误。用户可编辑草稿、重新生成失败回复、打开本地会话，或放弃草稿。

发送审阅显示准确渠道、接收人和完整正文；一次批准只对应这一次发送。保留 `sent`、`send_failed`、`delivery_unknown` 的区别；未知送达结果交由用户在平台核对，避免重复发送。

### 连接与生命周期

在已有 channel 模块下管理启用中的长连接和轮询任务，使用 CancellationToken。启用时启动；修改影响连接的配置时取消旧任务并使用新配置；停用、删除、退出时停止该渠道任务。重启应用后根据用户已保存的启用状态重新建立连接。

微信轮询持久化 `get_updates_buf`；每条入站消息关联发送所需的 `context_token`。回复使用该消息/联系人的正确 token，不能借用其他联系人的上下文。token、bot 凭据进入现有 SecretStore，前端只接收登录状态和必要非秘密字段。

飞书长连接应按官方协议处理帧、心跳、分片和事件确认。OneBot 反向 WebSocket 应处理 action echo 与平台响应。连接失败按实际错误显示，不自动改换协议。

UI 的连接检查只验证确实能够查询到的能力。例如飞书凭据获取成功不等于收到事件；OneBot 的账号/状态查询成功不等于回调可达；微信账号登录完成不等于已经产生入站消息。首次真实收信和平台发送确认单独展示。

## 拟扩展的接口与存储

以下是待实施接口，不是对当前仓库既有接口的描述。实现前应结合现有 API 风格冻结最终 DTO。

| 接口 | 用途 |
| --- | --- |
| `GET /api/channels/presets` | 内置与用户回复预设 |
| `POST /api/channels/presets` | 创建自定义预设 |
| `PUT /api/channels/presets/:id` | 编辑自定义预设 |
| `DELETE /api/channels/presets/:id` | 删除未被引用的自定义预设；被引用时要求先改选 |
| `POST /api/channels/presets/:id/preview` | 调用真实模型生成本地试用结果 |
| `DELETE /api/channels/:id` | 停止并删除渠道及相应凭据；处理消息保留策略要在确认界面说明 |
| `POST /api/channels/:id/check` | 返回各检查项和实际观察结果 |
| `POST /api/channels/:id/login` | 启动微信扫码授权 |
| `GET /api/channels/:id/login` | 查询扫码状态和有效二维码信息 |
| `DELETE /api/channels/:id/login` | 取消当前扫码 |
| `POST /api/channels/:id/messages/:message/regenerate` | 明确重新生成回复草稿 |

扩展 Channel 的 `connection_mode`、`preset_id`、实际运行状态及最近错误；增加回复预设存储、微信游标和消息上下文元数据。凭据继续使用 SecretStore。新增结构只服务渠道功能，不改造全局数据库、聊天 SSE 或其他工作流接口。

## 实现责任划分

Luna / xhigh 可负责独立工作包：协议适配器、预设与数据/API、前端实现。主代理负责冻结 DTO、共享集成点、审查、最终集成和桌面验收。并行编辑前为每个工作包指定独占文件；`AppServer`、router、数据库 schema 和公共类型由一个集成人统一处理。

拟新增文件集中在 `backend/src/modules/channel/`、`frontend/src/features/channels/` 和相应测试/证据目录；这些是计划目录，具体文件名在实施时按现有结构确定。需要的 WebSocket、飞书 protobuf、微信二维码依赖应在选型时核对官方协议与项目已有依赖，仅增加实际需要的库。

## 验收

1. 后端运行 `cargo fmt`、`cargo fmt --check`、`cargo check`，以及渠道、预设、权限相关测试；不因为本任务对其他脏文件做无关格式重写。
2. 前端运行生产构建及有意义的渠道/预设交互测试。检查各平台表单、验证错误、加载失败、配置保存、删除、预设绑定、消息更新和发送审阅。
3. 用受控平台服务验证协议、重复事件、发送确认、错误响应、取消和重启行为。受控服务证据明确标注，不算真实账号验收。
4. 在当前 Tauri 桌面检查页面、表单、主题、滚动、键盘操作和交互，保持用户既有配置与其他页面工作。
5. 使用用户授权的真实平台账号完成接入、收到真实消息、真实模型生成、审阅、平台确认发送。账号授权和联系人由用户实际选择；不伪造连接状态，不虚构收发结果。
6. 如果没有可用平台账号，功能代码、构建、受控协议和桌面交互可以分别给出证据；外部账号收发明确为待用户授权/待验收，不能报告全部真实收发已完成。
