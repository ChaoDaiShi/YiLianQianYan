# YiLianQianYan v0.9.0 Release Packaging Design

## Goal

Produce a reproducible Windows x64 NSIS installer for YiLianQianYan v0.9.0, verify the packaged artifact, and document the release boundary without changing Agent runtime behavior.

## Release boundary

- Windows x64 NSIS is the authoritative v0.9.0 release artifact.
- MSI remains out of scope because the v0.8 WiX path could not encode the Chinese product name reliably.
- macOS `.app` and `.dmg` builds remain available only through explicit macOS commands; they must not affect the default Windows build.
- Code signing, Apple notarization, auto-update, and release CI are separate follow-up work. An unsigned artifact must never be described as signed.
- Existing application data is preserved. Packaging must not add database migrations or alter Agent, MCP, approval, SSE, or security semantics.

## Configuration

The release version is `0.9.0` across the backend crate, Tauri crate/configuration, frontend package, root package, Cargo lockfile, and MCP client metadata. Runtime code should derive its client version from the backend crate version where practical so later releases have fewer independent literals.

The default Tauri bundle target is `nsis`. Platform-specific commands override that default:

- Windows: `npm run build:windows`
- macOS current architecture: `npm run tauri:build:macos`
- macOS universal: `npm run tauri:build:macos:universal`

## Build flow

The Windows release script performs these steps in order:

1. Verify that it is running on Windows and that Node.js, npm, Rust, and Cargo are available.
2. Verify all user-owned version declarations equal `0.9.0`.
3. Run frontend tests and the production frontend build.
4. Run Rust formatting checks, workspace checks, and workspace tests with the lockfile.
5. Build the Tauri NSIS bundle in release mode.
6. Locate exactly one v0.9.0 x64 installer, calculate SHA-256, and write a sibling checksum file.

The script stops on the first failed gate and never reports a release artifact unless the expected installer exists.

## Artifact verification

Automated verification covers:

- expected installer filename and non-zero size;
- SHA-256 generation;
- silent installation into a uniquely named temporary directory;
- presence of the installed executable and uninstaller;
- silent uninstall and removal of the temporary installation directory.

Manual acceptance remains required for visible window launch, non-blank UI, backend health, core task execution, clean shutdown, restart, and persisted settings. Automated packaging evidence does not replace this GUI acceptance.

## Release documentation

The repository records:

- v0.9.0 release notes;
- a v0.9.0 release checklist with command evidence and unresolved gates;
- the installer filename, byte size, and SHA-256 after a successful build;
- known limitations, including unsigned binaries and any dependency audit findings.

## Error handling and safety

- Missing prerequisites, version drift, test failures, build failures, missing artifacts, or failed install/uninstall smoke tests fail the release gate.
- Build scripts never delete repository data or broad directories.
- Temporary install verification uses one resolved directory below the system temporary directory and only removes that exact directory after containment validation.
- No secret values are printed or bundled intentionally.

## Alternatives considered

1. Build every platform from one default Tauri target list. Rejected because platform-specific bundle types can make the Windows release path fail or become ambiguous.
2. Publish both MSI and NSIS. Rejected for v0.9.0 because the known Chinese-name WiX encoding issue has not been resolved.
3. Use NSIS as the Windows release artifact and keep macOS explicit. Selected because it matches the proven v0.8 release path and minimizes new packaging risk.
