# v1.1 Readiness

> What R1 and R2 put in place for the v1.1 line (Identity, Cloud Gateway, Web
> Surface), and what a v1.1 branch would still have to build.
> Scope note: R2 was explicitly forbidden from starting v1.1 work. This document
> only records state, and does not plan the work.

## What v1.1 can now rely on

### A surface boundary that is already layered

`api/` handlers parse, delegate and map; the decisions live in
`modules/*/application`. A gateway in front of the REST surface would sit above
`app/router.rs` without reaching into a domain, because no domain calls upward
into `api/` — `domain_layers_do_not_import_transport` (backend) and the frontend
boundary checks both enforce that direction.

### One place that knows how to reach the backend

`frontend/src/core/api/http.ts` owns `API_BASE`, the control-session header and
both fetch wrappers. Every domain module imports its transport from there. A web
surface pointing at a remote gateway changes `API_BASE` (an env var,
`VITE_API_BASE`) and the control-session source — not fifteen modules.

Before R2 that was not true: `legacy.ts` held the transport inline and each
domain borrowed it. That is the concrete v1.1-relevant result of S6.

### A named public API

[public-api-policy.md](../architecture/public-api-policy.md) separates the
supported Product Public Contracts (REST, command, event, projection, and the
MCP/skill/capability/resource/artifact contracts) from the workspace-internal
host API and from internal implementation. A cloud surface is a consumer of the
first layer, and that layer is now written down rather than inferred from which
`pub` items happen to exist.

### A separation between the desktop shell and the backend

`surfaces/desktop/` is the only place a static `@tauri-apps/*` import is allowed;
everything else reaches the shell through a dynamic import. The backend is a
library plus a standalone `yilian-server` binary, and `AppServer` is constructed
by `app::bootstrap` rather than by the Tauri entry point.

### Identity-adjacent concepts that already have one owner

- **Secret lifecycle** — KEEP / REPLACE / DELETE in
  `modules/settings/application/secret_lifecycle.rs`, with four pinning tests.
  An identity layer that stores credentials should reuse that state machine
  rather than invent a second one.
- **Subject** — `safety::SecuritySubject`, resolved server-side
  (`SecuritySubject::local_user()`); no request body supplies a subject today.
  That is the seam a real identity would replace.
- **Tenancy-free assumptions** — `db/` is a single local SQLite file and
  `workspace/` treats the local filesystem as the root. Both are single-tenant
  by construction.

## What is genuinely absent

- **No authentication or session layer.** `ControlSession` is a local
  process-scoped token guarding the loopback API, not an identity. It is
  explicitly not a user credential.
- **No remote transport.** `API_BASE` defaults to `http://127.0.0.1:9420`; there
  is no TLS, no gateway, no retry/auth middleware.
- **No tenancy.** No tenant column, no per-tenant storage root, no migration
  namespace for it.
- **No Web Surface.** `surfaces/workspace/` is the desktop route table; there is
  no browser-targeted shell, and the Tauri boundary is enforced only at the
  import-shape level.
- **No server-side session or event fan-out beyond the local process.**
  `shared/event` is an in-process hub.

## Stop conditions a v1.1 branch would hit

- `DB_SCHEMA_CHANGE_REQUIRED` — identity and tenancy need new tables and a
  migration namespace. The current namespaces are Shared `0–999` and v1
  `1000–1999`; v2 owns its own and this branch must not borrow it.
- `SHARED_CONTRACT_CHANGE_REQUIRED` — an event or command envelope carrying
  identity would change `shared/`, which is the Protected Kernel.
- `PUBLIC_API_CHANGE_REQUIRED` — the REST surface is frozen at 178 handlers with
  no method, path or handler-signature change in R1 or R2. Auth adds behaviour to
  existing paths (a middleware) rather than new paths, or it is a versioned
  surface.

## Conclusion

R2 leaves v1.1 with **a clean seam, not a head start**. The transport is in one
place, the supported contracts are named, the layering direction is enforced by
tests, and the local-only assumptions are identifiable. Nothing about identity,
tenancy or remote transport exists, and R2 deliberately did not start any of it.
