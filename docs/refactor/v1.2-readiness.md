# v1.2 Readiness

> What R1 and R2 put in place for the v1.2 line (Harness Router, Repository
> Skill Forge, Capability Evolution), and what a v1.2 branch would still have to
> build.
> Scope note: R2 was explicitly forbidden from starting v1.2 work. This document
> only records state, and does not plan the work.

## Harness Router

### What exists

The task harness is a real, single execution path with one owner:

- `modules/task/harness.rs` (`TaskHarness`) and
  `modules/task/application/execution_service.rs` — executor resolution, the
  adapter registry, dispatch folding and validation policy. R2 / S1 moved this
  out of the HTTP layer precisely so a router could exist without a route.
- `modules/workflow/application/run_service.rs` — `execute_for_task_harness`,
  which reuses the persisted `WorkflowRun` rather than a second state machine.
  R2 / S2 moved it out of `api/`, and the task harness now reaches it directly
  instead of through the `crate::api::workflow_runtime` facade.
- `modules/task/executor.rs` + `executor_ref.rs` — `ExecutorKind`,
  `ExecutorResolver`, `ResolvedExecutionPlan`, and the `executor_ref` URI a node
  carries.
- `modules/task/adapters.rs` — `AdapterRegistry`, `ExecutorDispatch`, and the
  command / workflow / capability / agent adapters behind one dispatch.

So "route a step to a harness" already has a shape: resolve an `executor_ref` to
an `ExecutorResolver`, produce a `ResolvedExecutionPlan`, dispatch, fold the
outcome. A router is a policy over that, not a new mechanism.

### What is absent

- **No routing policy.** `executor_resolver` resolves exactly one node's
  `executor_ref`. There is no rule that picks between harnesses for the same
  step, no cost/latency/quality signal, and no fallback when a harness is
  unavailable. Everything needed to build that is in place; none of it exists.
- **No harness capability declaration.** A harness does not advertise what it is
  good at, so selection has nothing to select on beyond the node's own ref.
- **No cross-harness verification.** Each adapter folds its own outcome; there is
  no shared "did this actually succeed" step above them.

### Where the seams are

`modules/task/adapters.rs` (`ExecutorDispatch`, `AdapterRegistry`) and
`modules/task/executor.rs` (`ResolvedExecutionPlan`) are the two places a router
would plug in. Both are `modules/task` internals today, so a v1.2 branch either
extends them in place or promotes them — and promoting them is a
`SHARED_CONTRACT_CHANGE_REQUIRED` conversation if it touches `shared/`.

## Repository Skill Forge

### What exists

A complete, reviewed skill lifecycle with a file store:

- `modules/memory_skill/` — `candidate` → `review` → `version`, with `evidence`,
  `sensitivity`, `validator`, `repository`, `service` and `store`.
- Two deliberate gates: **creation requires an explicit authorization flag**,
  **install requires an explicit confirmation flag**. Neither is automatic.
- The store treats the database as *not* the truth for the file: a rule edited
  outside the service is refused, not overwritten (`modules/memory_skill/store.rs`,
  pinned by tests).
- `tools/skill.rs` — `SkillDiscovery`.

### What is absent

- **No ingestion from a repository.** Nothing reads a Git repository, a package
  index, or a remote catalogue. `candidate` is created from local evidence only.
- **No provenance or signing.** A managed skill records its versions but not
  where it came from or who signed it.
- **No dependency resolution between skills.** Each is standalone.
- **No capability-evolution engine.** `ownership.md` states this explicitly: the
  stable concepts exist, "no such engine exists here, and none is anticipated in
  code."

### Why this is the right starting point

The review lifecycle and the explicit gates are exactly the policy a forge must
not bypass. A forge that fetched and installed without them would be a security
regression, and the gates are enforced in code, not convention.

## Capability Evolution

### What exists

A registry that already models the whole surface:

- `modules/capability/registry.rs`, `provider.rs`, `model.rs` — one
  `CapabilityDescriptor` covering tool / mcp_tool / subagent / agent / workflow /
  skill, with `kind`, `provider`, `risk`, `permissions`, `status` and `metadata`.
- `modules/capability/runtime_providers.rs` + `builtin.rs` — the providers.
- `modules/capability/imports.rs`, `import_owner.rs`, `import_store.rs` — an
  import path with an owner and a store, which is the nearest thing to evolution
  that exists.
- Read side: `api/capabilities.ts` (frontend) over
  `modules/capability/api`, and `listCapabilities` / `getCapability` /
  `refreshCapabilities`.

### What is absent

- **No proposal or promotion path.** `refreshCapabilities` re-reads what
  providers already advertise; it does not propose a *new* capability.
- **No evaluation.** Nothing measures whether a capability is worth keeping, and
  `status` is set by the provider, not by observed outcomes.
- **No lifecycle beyond enabled/disabled.** There is no deprecation, no
  supersede, no rollback of a capability.
- **No learning from executions.** Task outcomes are recorded in the task domain
  (`modules/task/timeline.rs`, `projection.rs`) and are not fed back to the
  registry.

### Where the seams are

`modules/capability/registry.rs` (registration) and the `import_owner` /
`import_store` pair (provenance) are where an evolution engine would attach.
`CapabilityRisk` and `CapabilityPermission` already give it something to gate on.

## Stop conditions a v1.2 branch would hit

- `SHARED_CONTRACT_CHANGE_REQUIRED` — a harness outcome or capability lifecycle
  event would extend `shared/event`, the Protected Kernel.
- `DB_SCHEMA_CHANGE_REQUIRED` — repository skills need provenance tables; a
  capability lifecycle needs history. v1 owns `1000–1999`; nothing may borrow
  v2's namespace.
- `SECURITY_SEMANTICS_CHANGE_REQUIRED` — a forge that installs anything must keep
  `safety::SecurityExecutionGateway` and the approval path as the only route to
  a side effect. `gateway_managed_mcp_*` (3 tests) and `security_execution`
  (10 tests) pin that today.

## Conclusion

R2 leaves v1.2 with **the concepts and the seams, and no engine**. Every one of
the three v1.2 features has a named owner, a listed invariant and a test that
pins it; none of them has a mechanism. That is deliberate — R2's mandate was to
make the existing boundaries real, not to start the next line.
