# 第一章 项目背景与开发目标

## 1.1 项目背景

忆涟千言定位为任务驱动的自适应 AI 工作环境，致力于将人工智能模型、任务执行能力、用户记忆、工作空间、桌面交互与外部应用生态统一到一个可持续扩展的软件系统中。

本轮升级围绕现有系统的基础能力补齐与交互体验提升展开。

长期目标并非开发一个拥有大量功能的普通 AI 聊天客户端，而是建立一个具备用户认知、持续上下文、长期记忆、多模型协同、可扩展工作空间与桌面环境融合能力的个人智能计算环境。

系统应允许用户继续使用已有软件，通过协议、插件、适配器和自动化机制将外部软件接入忆涟千言，而不是强制用户迁移到封闭生态。

## 1.2 核心开发目标

本轮确定八个能力方向。

| 编号 | 能力体系 | 开发目标 |
|---|---|---|
| UC-01 | 初始化与用户画像 | 建立首次启动引导、用户认知及渐进式画像更新机制 |
| UC-02 | 多模态富交互聊天 | 支持文本、图片、图表、可交互 UI、任务状态与成果输出 |
| UC-03 | 本地长期记忆 | 接入轻量向量模型，建立混合检索、记忆版本和关系管理 |
| UC-04 | 无限页面工作空间 | 实现 Notion 式嵌套页面、块编辑、知识关联与 AI 协作 |
| UC-05 | 模型与上下文管理 | 统一 API、CLI、本地模型、会话记录与上下文编排 |
| UC-06 | 智能桌宠 | 完善 Live2D、交互、事件响应、屏幕感知与主动能力 |
| UC-07 | 实验性桌面化 | 构建桌面视觉层、桌面组件与主题编排系统 |
| UC-08 | 开放生态兼容 | 兼容 Wallpaper Engine 等外部软件及开放协议 |

上述能力之间存在大量共享逻辑。本轮实施必须以公共基础设施优先的方式组织，避免分别实现八套独立数据、权限和事件系统。

## 1.3 产品设计原则

**原则一：本地优先。** 用户画像、聊天记录、工作空间、长期记忆及基本配置应能够在本地持久化。云端模型和外部服务不能成为读取本地资料的唯一途径。

**原则二：统一事实来源。** 用户会话、工具执行、任务变更等由统一记录系统管理。上下文缓存、记忆索引和界面状态是可以重建的派生数据。

**原则三：能力解耦。** 任何特定模型、CLI、壁纸引擎、笔记软件或桌宠渲染器都不能成为核心业务逻辑的不可替代依赖。

**原则四：开放兼容。** 优先通过公开 API、协议、SDK 和可授权的本地接口连接成熟生态。

**原则五：安全可撤销。** 系统权限按资源、动作、作用域和期限划分。对于屏幕感知、文件修改、命令执行等敏感能力，必须能够查看授权并立即撤销。

**原则六：可观测、可恢复。** 所有具有副作用的任务都需要明确状态、错误信息、日志及恢复策略。

**原则七：按需运行。** 本地模型、桌宠、外部软件及后台服务应受统一资源管理约束，不得无条件全部常驻。

**原则八：增量兼容。** 尽可能保持现有 API、数据库记录、前端页面及插件接口兼容。重大改变通过版本化迁移完成。

## 1.4 本轮交付边界

本轮应完成核心架构、主要功能链路以及能够证明系统能力的真实集成。

必须交付：

- 初始化、用户画像、配置持久化及已有用户迁移机制。
- 跨模型的统一会话记录与上下文编排。
- 至少覆盖 API、一个深度 CLI 和一个本地运行时的模型接入。
- 富交互消息协议、标准组件与交互状态恢复。
- 本地向量化、记忆检索、用户记忆管理。
- 无限嵌套页面、基本块编辑与 AI 内容引用。
- Live2D 桌宠及获得用户授权的屏幕交互能力。
- 第三方壁纸引擎基础控制和桌面主题管理。
- 插件兼容桥、权限管理、异常恢复及验收测试。

允许以实验标记交付：

- 深度 Windows Desktop Surface。
- 外部角色运行时的高级动作同步。
- 自动生成复杂交互式应用。
- 跨多个外部软件的自主长流程编排。
- 复杂三维记忆可视化。
- 多端实时协作及桌面 Shell 深度接管。

实验能力必须具有独立开关，不得影响稳定功能使用。

# 第二章 总体技术架构

## 2.1 系统分层

建议采用以下逻辑分层：

**L1：Surface Layer（用户交互层）**

包含主桌面客户端、Web Surface、聊天界面、工作空间、桌宠窗口、悬浮交互层和实验性 Desktop Surface。

**L2：Interaction & Application Layer（交互与应用层）**

包含用户行为接收、富交互渲染协议、事件派发、页面管理、会话编排和应用命令。

**L3：Domain Service Layer（核心领域服务层）**

包含用户画像、会话、上下文、记忆、任务、工作空间、模型管理、权限与资源管理。

**L4：Capability & Ecosystem Layer（能力与生态层）**

包含模型适配器、CLI 适配器、MCP 运行时、插件运行时、Wallpaper Provider、Live2D Runtime、外部软件适配器及 Windows Native Bridge。

**L5：Persistence & Runtime Layer（持久化与运行层）**

包含 SQLite、全文检索、向量索引、文件资源仓库、缓存、后台作业、Harness Runtime 和操作系统适配。

推荐调用关系：

Surface → Application Service → Domain Service → Capability Adapter → External System

横向基础服务：

Event Bus、Permission Engine、Resource Orchestrator、Observability、Configuration Registry。

任何 Surface 均不得绕过权限服务直接执行高权限系统操作。

## 2.2 工程模块建议

以下是逻辑模块名称，不要求立即按名称创建独立 crate 或目录。

| 模块 | 职责 |
|---|---|
| `core-profile` | 用户资料、偏好、初始化 |
| `core-conversation` | 会话、分支、消息与事件记录 |
| `core-context` | 上下文快照、压缩、缓存与 Token 预算 |
| `core-memory` | 记忆提取、版本、检索、关系 |
| `core-workspace` | 页面树、内容块、引用与版本 |
| `core-model` | 模型注册、能力声明、模型路由 |
| `core-agent` | 任务生命周期、执行状态与工具调度 |
| `core-permission` | 授权检查、策略、撤权 |
| `core-resource` | 资源预算、进程生命周期 |
| `core-ecosystem` | 第三方能力发现与适配器 |
| `surface-rich-ui` | 富交互消息和组件渲染 |
| `surface-live2d` | 原生 Live2D 角色表现 |
| `surface-desktop` | 桌面主题、覆盖层和桌面组件 |
| `platform-windows` | Windows 原生窗口、屏幕及系统接口 |

已有模块与上述职责一致时，应直接扩展现有实现，不重复建立同职能服务。

## 2.3 技术栈建议

坚持原项目技术栈优先原则。

在现有 Rust 后端与 Web 前端架构能够满足要求的前提下，建议继续使用：

| 技术领域 | 推荐技术 |
|---|---|
| 核心后端 | Rust |
| 桌面宿主 | 保留当前宿主；如采用 Tauri，优先利用既有 IPC 与窗口机制 |
| 前端 | 延续当前框架，避免为了新功能重新选型 |
| 数据持久化 | SQLite |
| 全文索引 | SQLite FTS5 |
| 向量索引 | sqlite-vec 或经验证的等价适配 |
| 富文本编辑 | Tiptap / ProseMirror |
| 状态通信 | 现有 IPC、SSE 或 WebSocket |
| 事件模型 | 内部版本化事件协议 |
| AI 接入 | API / CLI / Local Runtime / Agent Adapter |
| 角色渲染 | Live2D Cubism SDK |
| 系统能力 | Windows Native Bridge |
| 密钥存储 | Windows Credential Manager / DPAPI |

不因为引入一个新能力而强制更换整个前端框架或数据库。

# 第三章 全局数据与事件协议

## 3.1 统一事件系统

必须建立统一的事件模型，供聊天、任务、工作空间、记忆、桌宠及生态适配器复用。

建议事件字段：

| 字段 | 说明 |
|---|---|
| `event_id` | 全局唯一事件 ID |
| `schema_version` | 事件结构版本 |
| `stream_id` | 所属事件流 |
| `sequence` | 流内递增序号 |
| `event_type` | 事件类型 |
| `subject_id` | 产生事件的主体 |
| `scope_id` | 用户、会话、页面或任务作用域 |
| `correlation_id` | 关联同一业务操作 |
| `causation_id` | 直接触发本事件的上游事件 |
| `idempotency_key` | 重试去重键 |
| `payload` | 结构化事件内容 |
| `created_at` | 事件产生时间 |

事件写入应具备以下特性：

1. 重要状态变更采用事务提交。
2. 同一事件流维护确定的事件顺序。
3. 消费者具备幂等处理能力。
4. 支持断线后从游标重新订阅事件。
5. 失败事件不能静默消失。
6. 未完成的流式输出需要明确状态。
7. 不在事件中直接保存 API 密钥等敏感凭证。

实际工程中可以采用“至少一次传递 + 幂等消费”的可靠机制，不要求所有外部系统提供不现实的全局恰好一次执行保证。

## 3.2 统一任务生命周期

任务建议统一采用：

`Created → Queued → Running → Completed`

允许分支状态：

- `AwaitingApproval`
- `Paused`
- `Cancelling`
- `Cancelled`
- `Failed`
- `Recovering`
- `Blocked`

任务记录必须具有任务 ID、执行器 ID、开始与结束时间、恢复检查点、操作日志、结果引用及错误信息。

任务恢复时，系统应先判断此前操作是否已经成功产生副作用，再决定继续执行、跳过、人工确认或重新运行。

不得简单地重新发送整个任务而不考虑重复修改文件、重复发送消息等风险。

## 3.3 统一资源引用

聊天、工作空间、任务、记忆应使用资源引用进行关联，而不是分别复制完整内容。

建议基础资源类型：

`conversation、message、page、block、asset、memory、task、tool_result、external_resource`。

资源引用必须包含资源 ID、类型、来源及必要的权限范围。

资源删除、授权撤回、文件迁移时，依赖它的组件应能识别资源已不可用，并显示合理的降级状态。

# 第四章 初始化与用户画像系统

## 4.1 功能组成

建立两个独立服务：

- `OnboardingService`：负责首次启动引导、完成状态及环境初始化。
- `UserProfileService`：负责用户身份、偏好、个性化配置及后续画像更新。

初始化流程不应只执行一次后就失去编辑能力。

## 4.2 首次启动流程

**步骤 1：欢迎与隐私说明**

说明忆涟千言的主要能力、数据保存位置、AI 服务使用方式，以及哪些功能涉及权限。

用户可以跳过非必要的个人资料填写。

**步骤 2：基本资料**

可选设置称呼、语言、时区、职业或学习背景、主要使用场景。

其中职业、兴趣等不能被视为永久不变的身份事实。

**步骤 3：交流习惯**

设置回答长度、表达风格、主动建议程度、技术解释深度和是否默认展示详细执行过程。

**步骤 4：权限与记忆**

分别选择长期记忆、屏幕感知、麦克风、文件访问和外部模型数据传输权限。

这些授权必须彼此独立，不能以同意初始化协议替代所有敏感权限。

**步骤 5：设备和模型检测**

检测 CPU、GPU、可用内存、操作系统、已安装 CLI、本地模型服务和可发现的外部应用。

检测失败不得阻止使用基础聊天功能。

**步骤 6：外观与工作空间**

选择主题、默认工作空间、桌宠启用状态和页面布局。

**步骤 7：初始化提交**

原子化保存必要配置，生成个人空间，记录初始化版本，进入主界面。

## 4.3 渐进式用户画像

系统应允许在后续对话中逐步理解用户。

建议画像来源分为：

- 用户明确填写。
- 用户明确要求记录。
- 从长期互动中提取的候选偏好。
- 已授权外部资料中的相关信息。

每个画像事实应具有来源、时间、有效性与可编辑状态。

对冲突内容执行“发现冲突 → 评估可信度 → 生成更新建议 → 按策略提交”。

重要身份资料不得因一次模型推测被无提示地覆盖。

## 4.4 数据结构

建议表：

`user_profiles`

字段：`user_id、display_name、language、time_zone、preferences_json、created_at、updated_at`。

`onboarding_progress`

字段：`user_id、flow_version、current_step、status、draft_json、completed_at`。

`profile_facts`

字段：`fact_id、user_id、fact_type、value_json、source_ref、confidence、status、valid_from、valid_to`。

## 4.5 验收标准

- 新安装用户可完成初始化。
- 用户可以跳过非关键内容。
- 初始化中途退出后可恢复。
- 既有用户升级后不会被强制清空资料。
- 重启后配置和权限保持一致。
- 用户可以重新运行初始化向导。
- 删除画像字段后，相关缓存和可检索副本同步失效。

# 第五章 多模态富交互聊天系统

## 5.1 目标

聊天系统从单纯文字展示升级为多种内容共同构成的交互式结果界面。

模型输出与前端渲染必须分离。

模型负责描述内容、组件数据和交互意图；客户端负责验证、渲染及执行获得授权的操作。

## 5.2 标准消息类型

第一批标准内容类型：

| 类型 | 功能 |
|---|---|
| `text` | 文本与 Markdown |
| `code` | 带语言信息的代码 |
| `math` | 数学公式 |
| `image` | 图片与图片集合 |
| `file` | 文件引用与预览 |
| `table` | 可排序或筛选表格 |
| `chart` | 柱状图、折线图、散点图等 |
| `form` | 表单与输入组件 |
| `interactive_card` | 带交互操作的卡片 |
| `task_status` | 执行状态与审批 |
| `artifact` | 可继续编辑或引用的成果 |
| `custom_view` | 受控沙箱内的复杂交互视图 |

消息可由多个内容块组成，允许在同一回复中交替出现文字、图片、图表与可操作组件。

## 5.3 Rich Response Runtime

建立以下组件：

1. `RichResponseParser`：接收模型的结构化输出。
2. `ContentSchemaValidator`：校验内容结构及版本。
3. `ComponentRegistry`：注册允许渲染的组件。
4. `RichContentRenderer`：执行真实前端渲染。
5. `InteractionDispatcher`：接收用户操作。
6. `ComponentStateStore`：保存可交互状态。
7. `ArtifactBridge`：将结果转为工作空间资源。

第一阶段采用预定义组件目录。

复杂自定义交互视图必须进入隔离沙箱，不允许模型直接在宿主 WebView 中执行任意脚本。

## 5.4 外部协议兼容

建议参考：

- AG-UI：负责 Agent 与用户界面之间的事件和状态交互。
- A2UI：负责声明式生成 UI 的描述与更新。
- 内部 Rich Content Schema：负责忆涟千言自身的数据持久化和版本稳定性。

具体架构为：

外部协议 → Protocol Adapter → 内部 Rich Content Schema → Component Registry → Surface。

外部协议格式不得直接成为不可迁移的数据库核心结构。

由于相关规范仍存在版本演进，需要对外部适配器执行版本兼容测试。

## 5.5 用户交互回传

每个可交互组件应拥有：

`component_id、component_type、schema_version、state_version、permissions、available_actions`。

用户点击按钮、修改滑块或提交表单时，生成交互事件。

事件由对应业务服务处理，不能仅依靠前端状态变化伪装成功。

界面必须明确区分：

- 本地界面状态已修改。
- 操作请求已发送。
- 后端操作成功。
- 后端操作失败。
- 操作等待用户审批。

## 5.6 图片与多模态资源

模型生成图片或接收图片后，应将图片作为独立资源保存。

消息内容仅保存引用和元信息，包括资源 ID、MIME 类型、分辨率、来源和必要的生成参数。

支持延迟加载、缩略图和原始资源查看。

对于依赖外部 URL 的内容，要处理失效、授权和缓存策略。

## 5.7 富交互状态恢复

用户关闭程序后重新打开会话，标准内容与组件状态应能够恢复。

不允许出现文本仍在但图表、任务卡片或用户已填写的内容全部消失的情况。

临时预览与持久化成果应有区别：临时预览可以回收，而正式保存的 Artifact 必须拥有稳定资源 ID。

## 5.8 验收标准

- 支持至少文本、图片、表格、图表、表单、任务状态六类内容。
- 同一消息可包含多个不同内容块。
- 可交互组件能够正确回传用户操作。
- 刷新和重启后可以恢复已提交的组件状态。
- 无效 Schema 不会导致主程序崩溃。
- 恶意组件描述不能执行未授权系统操作。
- 聊天结果可保存到工作空间。

# 第六章 统一模型、CLI 与上下文管理系统

## 6.1 目标

建立统一模型调用接口，兼容 API、CLI、本地模型和外部 Agent。

解决不同模型间聊天记录分裂、上下文不一致、外部会话难恢复、工具执行过程不可追踪等问题。

本模块是其他智能能力的重要基础设施。

## 6.2 模型提供者接口

建议定义 `ModelProvider` 抽象。

基础能力：

- `discover_models`
- `get_capabilities`
- `create_session`
- `resume_session`
- `send_turn`
- `stream_events`
- `cancel_turn`
- `close_session`

不同提供者允许声明不支持的操作，而不是由主系统假定所有模型都有相同能力。

能力描述至少包含：

`text、vision、image_generation、tool_use、structured_output、streaming、native_session、session_resume、context_limit`。

未确认的能力应保持未知，不得通过猜测标记为支持。

## 6.3 首批模型接入

**API Provider**

兼容已有云端接口和必要的标准模型调用接口。

保留鉴权、用量统计、流式输出、工具调用和结构化输出能力。

**Codex Adapter**

深度集成优先采用 Codex App Server。

同步线程、轮次、工具运行、审批、执行结果和错误状态。

非交互式执行可作为独立模式使用 `codex exec`。

**Gemini CLI Adapter**

采用 Headless 模式及结构化 JSON/JSONL 事件。

解析消息、工具调用、执行结果、会话信息和失败状态。

**Local Model Adapter**

适配现有本地模型服务。

建议先支持一个已验证的本地运行时，再通过通用 Provider 接口扩展。

## 6.4 统一会话事实记录

所有模型的可观察结果必须统一记录为忆涟千言的会话事件。

重点保存：

- 用户输入。
- 模型可展示的回复。
- 工具调用及工具结果。
- 任务状态。
- 用户审批。
- 附件引用。
- 可展示的错误信息。
- 模型使用情况。
- 会话切换与恢复记录。

不要求也不应该试图提取模型不可公开的内部推理状态。

## 6.5 Shared Context Pool 设计

正式划分四个子系统。

**Conversation Event Store**

负责保存完整的可观察会话事实。

**Context Orchestrator**

根据当前模型、任务、用户配置和权限，生成当前请求的上下文。

**Shared Context Cache**

缓存近期消息、摘要、Token 统计和可复用的上下文片段。

**Provider Session Registry**

保存忆涟会话与外部模型原生会话的映射。

必须明确：共享缓冲池不是所有模型共享一个可随意修改的消息数组。

## 6.6 上下文构造流程

建议流程：

1. 获取当前会话与分支。
2. 获取用户最近输入。
3. 获取任务状态与必要的工具结果。
4. 获取当前模型能力和上下文限制。
5. 选取最近相关对话。
6. 根据需要检索长期记忆。
7. 从已有摘要中取得历史信息。
8. 计算上下文预算。
9. 去除重复、过期和无权限内容。
10. 生成模型专属上下文包。
11. 保存上下文构造元信息。
12. 调用模型并持续记录后续事件。

Context Snapshot 建议包含：

`conversation_id、branch_id、model_id、event_cursor、summary_revision、memory_refs、tool_schema_version、token_budget、content_digest`。

## 6.7 模型切换策略

模型切换分为两类。

**原生会话恢复**

当目标提供者支持恢复原有会话且状态可信时，优先使用原生机制。

**上下文包迁移**

当切换到其他提供者时，使用统一事件日志、任务状态、摘要和记忆重新构造上下文。

两者不得混为一谈。

切换到新模型不能保证继承旧模型的隐藏内部状态，但必须尽可能完整地迁移可保存的用户信息、工具结果和任务上下文。

## 6.8 缓存失效

以下情况触发相关上下文缓存失效或重建：

- 用户编辑或撤回消息。
- 上下文摘要被更新。
- 关键记忆被修改或删除。
- 用户撤回相关权限。
- 模型或模型能力配置发生变化。
- 工具 Schema 发生不兼容变化。
- 会话发生分支。
- 重要任务状态发生变化。

缓存必须与用户及会话作用域隔离。

不同用户、不同权限环境之间不得复用未经检查的上下文。

## 6.9 并行会话与分支

同一主会话可以存在多个执行分支。

每个任务保留自己的执行上下文、状态和事件游标。

并行任务之间不得通过直接修改共享内存中的消息数组来改变彼此上下文。

合并分支时，应合并可观察结果和用户确认的结论，不直接拼接不相容的模型原生会话。

## 6.10 CLI 安全

CLI 进程应由受控进程管理器启动。

强制要求：

- 使用可执行文件路径及参数数组，避免未验证的字符串拼接进 shell。
- 为任务设置工作目录与可访问资源范围。
- 根据能力级别进行操作审批。
- 支持取消、超时和异常退出处理。
- 不将外部 CLI 的凭据复制到普通日志。
- 子进程退出后回收资源。
- 外部 CLI 的原生审批规则必须保留，不得由适配层偷偷绕过。
- 具备修改文件等副作用的任务应设置幂等和恢复策略。

## 6.11 验收标准

- API 模型与 CLI 使用统一会话视图。
- 外部 CLI 工具执行状态能够实时展示。
- 模型切换不丢失已有本地记录。
- 同一会话支持中断恢复。
- 不同分支上下文不会互相污染。
- 缓存删除后能够根据持久化数据重建。
- CLI 异常退出不会损坏会话数据库。
- 命令执行与文件修改遵守权限系统。

# 第七章 本地长期记忆系统

## 7.1 目标

为现有记忆系统增加本地语义向量化与混合检索能力。

同时完善记忆版本、来源、关系和生命周期管理。

向量索引只作为检索加速结构，不作为记忆本身的唯一存储形式。

## 7.2 记忆类型

建议至少包含：

- 用户画像记忆。
- 语义记忆。
- 情景记忆。
- 程序性记忆。
- 工作记忆。
- 记忆关系与演变记录。

普通聊天日志不自动等同于长期记忆。

只有通过提取、规则筛选及相应授权的候选内容，才可以进入长期记忆。

## 7.3 本地 Embedding 模型

默认候选：

`BAAI/bge-small-zh-v1.5`

其 512 维输出适合中文文本检索的轻量部署。

增强候选：

`Qwen/Qwen3-Embedding-0.6B`

支持最多 1024 维输出以及可配置维度，更适合中英文和技术文本混合场景，但实际性能仍需本地验证。

模型选择策略：

- 默认使用能够在 CPU 运行的轻量方案。
- 后台按需启动，不常驻占用 GPU。
- 用户可选择增强模型。
- 支持未来接入新的 Embedding Provider。
- 禁止不同模型、版本或维度的向量直接混入相同索引。
- 模型切换后启动受控重索引任务。

## 7.4 记忆提取链路

输入来源：

聊天事件、任务结果、用户编辑、工作空间内容和明确授权的外部资源。

处理过程：

1. 接收原始内容引用。
2. 识别候选事实。
3. 判定记忆类型。
4. 检查重复项。
5. 检查与现有记忆的冲突。
6. 计算可信度与适用范围。
7. 按用户记忆策略确认。
8. 保存记忆原文与来源。
9. 异步执行向量化。
10. 建立全文和向量索引。
11. 更新记忆关系图。

不得因为向量模型暂时不可用而丢弃已经确认的记忆。

## 7.5 存储设计

建议使用 SQLite 管理主数据。

`memory_items`

记录：

`memory_id、owner_id、scope_id、type、content、source_ref、confidence、status、revision、valid_from、valid_to、created_at、updated_at`。

`memory_revisions`

保存记忆历史版本。

`memory_relations`

保存记忆之间的关系与关联类型。

`memory_embedding_refs`

保存当前记忆版本对应的向量索引信息、模型版本、维度、状态及文本哈希。

FTS5 用于关键词检索。

sqlite-vec 用于本地向量检索。

由于 sqlite-vec 仍可能存在不兼容更新，必须通过 `VectorIndexAdapter` 隔离，不直接将扩展特定接口暴露到业务服务。

## 7.6 混合检索

建议支持：

- 全文检索。
- 向量相似度检索。
- 记忆类型过滤。
- 用户及项目作用域过滤。
- 时间与版本过滤。
- 关系图邻接扩展。
- 可选重排。

融合可先采用 RRF（倒数排名融合）等简单可解释的排序方法，随后根据真实评测再优化。

所有检索必须先执行权限过滤，不允许先检索不属于用户或任务的内容，再仅依赖模型自行忽略。

## 7.7 记忆更新与冲突

记忆更新不应直接覆盖旧文本。

建议采用版本式修改。

例如旧记忆“用户偏好简洁回答”后来被明确更正为“技术方案需要完整细节”，旧版本保留为历史，但不再默认进入当前上下文。

记忆关系应记录 `supersedes`、`supports`、`contradicts`、`related_to` 等语义关联。

## 7.8 记忆可视化

继续保留二维和三维记忆图的长期目标。

二维默认展示当前有效记忆之间的语义关系。

三维模式允许按照记忆的版本或变更历史展示时间层。

必须具备节点筛选、搜索、来源查看、版本切换和记忆操作入口。

图形结构是记忆数据库的可视化结果，不是独立的事实来源。

## 7.9 删除与隐私

用户删除记忆时，应同步处理：

- 当前有效记录。
- 相关检索索引。
- 可清除的派生缓存。
- 失效引用。
- 外部同步副本的撤销请求（如具备权限与接口）。

如果保留合法必要的审计元数据，不能包含用户要求清除的敏感记忆正文。

对无法立即删除的离线备份，应明确备份保留策略和恢复后的删除重放流程。

## 7.10 验收标准

- 本地向量化可以离线运行。
- 能够检索语义相近但用词不同的记忆。
- 索引丢失后能够重建。
- 修改记忆后不会继续检索到错误的旧版本。
- 支持追溯记忆来源。
- 用户可以关闭自动记忆功能。
- 记忆访问遵守用户与项目作用域。
- 重建向量索引时不阻塞普通聊天。
- 检索效果通过人工标注数据集评测，不仅凭主观演示判断。

# 第八章 无限页面工作空间

## 8.1 产品目标

建立类似 Notion 的自由页面组织体系，同时融合任务、聊天、知识、记忆和 AI 可操作内容。

“无限页面”指不施加人为固定嵌套层级限制，而不是一次加载无限数量的页面。

## 8.2 核心结构

`Workspace → Page → Subpage → Block`

页面树支持：

- 任意层级嵌套。
- 拖动排序。
- 移动与复制。
- 页面图标和封面。
- 收藏与最近访问。
- 页面模板。
- 全文搜索。
- 页面引用。
- 回收站和恢复。
- 导入与导出。

后台必须通过分页和增量加载管理大型页面树。

## 8.3 数据模型

`workspaces`

保存工作空间身份、所有者、默认配置和创建时间。

`pages`

字段包括：

`page_id、workspace_id、parent_page_id、title、icon_json、sort_key、revision、created_at、updated_at、deleted_at`。

`page_blocks`

字段包括：

`block_id、page_id、parent_block_id、block_type、content_json、sort_key、revision、created_at、updated_at`。

`page_revisions`

记录页面版本和可恢复的变更。

`page_links`

记录页面之间以及页面与其他资源之间的引用。

必须对页面父子关系执行环检测。

禁止将页面移动到自己的子孙节点下面。

## 8.4 Block 类型

首批实现：

- 段落、标题、列表、引用。
- 代码、公式、分隔线。
- 图片、文件、媒体。
- 表格、待办。
- 页面引用。
- AI 结果块。
- 任务块。
- 图表与可视化块。
- 交互式嵌入块。

复杂数据库、看板、时间轴可以后续作为专业块实现。

## 8.5 编辑器方案

建议基于 Tiptap/ProseMirror 的现有编辑能力构建块编辑器。

优先完成：

- 光标与选择。
- Markdown 常用快捷输入。
- Slash 命令。
- 块拖动。
- 自动保存。
- 撤销与重做。
- 页面版本恢复。
- 大文档性能优化。

协作编辑不作为第一轮必需功能。

如果后续需要多人实时协作，可研究 Yjs/CRDT，但必须先解决现有单机页面和 AI 修改的版本一致性。

## 8.6 AI 与页面协同

AI 必须能够在明确授权下：

- 创建页面。
- 在页面中插入内容块。
- 总结页面。
- 生成任务。
- 修改指定内容。
- 引用其他页面。
- 将聊天结果保存为内容块。
- 将页面作为任务上下文。

AI 修改已有内容时，应尽可能生成可查看的差异，并提供接受、撤销或恢复能力。

不允许未经明确授权自动覆盖重要文档。

## 8.7 外部生态

首批支持通用 Markdown 导入和导出。

预留：

- Notion 页面导入与连接。
- Obsidian Vault 读取。
- 通用文档格式转换。
- 外部资源链接。

外部页面可以采用复制导入、只读引用或受控同步三种模式。

不得默认将外部内容双向同步，也不得在没有冲突策略的情况下覆盖外部原文。

## 8.8 验收标准

- 可以创建多级嵌套页面。
- 页面树不允许产生循环。
- 大量页面可以分页加载。
- 内容自动保存。
- 页面可引用其他页面和聊天成果。
- AI 修改页面可撤销。
- Markdown 导入导出不应无提示丢失常见文本结构。
- 删除页面后可以按策略恢复。
- 页面权限与用户权限保持一致。

# 第九章 桌宠与屏幕感知系统

## 9.1 开发目标

桌宠不应是独立运行的简单动画角色，而应成为忆涟千言的交互 Surface。

桌宠使用系统已有的对话、模型、事件、任务和记忆能力。

## 9.2 系统组成

`PetRuntime`

负责桌宠整体生命周期。

`Live2DRenderer`

负责模型加载、绘制、动作、表情、物理及动画。

`PetInteractionController`

负责鼠标、拖动、点击、热区和交互动作。

`PerceptionGateway`

负责感知请求、授权、采集及数据过滤。

`PetBehaviorEngine`

根据用户操作、系统事件和角色配置生成行为意图。

`PetEventBridge`

负责桌宠与主程序的双向事件同步。

## 9.3 Live2D 兼容

以 Cubism SDK 兼容模型为主要目标。

需要兼容：

- 基础模型加载。
- 动作和表情。
- 模型缩放及位置。
- 口型同步。
- 鼠标注视。
- 触摸热区。
- 物理效果。
- 模型切换。
- 参数配置。

具体模型功能以模型自身资源和 SDK 支持情况为准。

不得假定任何第三方 Live2D 模型都包含完全相同的动作、参数或表情。

## 9.4 桌宠交互

支持：

- 拖动角色。
- 锁定位置。
- 点击与双击。
- 右键菜单。
- 输入框或语音调用。
- 消息气泡。
- 任务完成提示。
- 交互窗口打开与收起。
- 特定区域点击穿透。

桌宠需根据前台窗口、全屏软件和用户配置调整展示状态。

## 9.5 感知系统

感知按照风险分级。

**一级：内部事件感知**

读取忆涟自身的任务状态、工作空间事件和对话状态。

**二级：窗口元信息感知**

在授权范围内读取活动窗口及可公开获取的应用信息。

**三级：屏幕内容感知**

用户明确选择窗口或屏幕后，采集指定画面并调用视觉理解能力。

**四级：持续感知**

需要独立显式开启，限定目标、用途和持续时间，具备始终可见的状态指示及立即停止入口。

建议优先采用事件驱动、按需采样模式。

不允许将屏幕连续采集作为软件默认行为。

## 9.6 Windows 屏幕捕获

使用 Windows 正式图形捕获接口作为优先方案。

通过系统提供的窗口/显示器选择机制获取采集目标。

原始画面默认仅在内存中短暂处理。

如需上传给云端视觉模型，必须检查用户授权和数据传输策略。

敏感窗口可设置为排除项。

感知结果进入日志或长期记忆，需要另行判断是否符合记录策略。

## 9.7 桌宠行为决策

建议采用事件与状态驱动的行为模型。

输入：

用户交互、任务状态、角色状态、资源预算、可用能力和获授权的感知信息。

输出：

动作、表情、消息、提示、应用打开请求或待审批操作。

桌宠主动行为不能无约束地不断产生模型请求。

需要配置主动性等级、冷却机制、勿扰模式和资源预算。

## 9.8 外部角色生态

建立角色提供者接口。

第一种：

`NativeLive2DProvider`

由忆涟自己渲染和控制。

第二种：

`VTubeStudioProvider`

通过公开的 WebSocket 插件 API 与外部 VTube Studio 实例通信。

可以研究模型状态、热键、表情和事件同步。

外部软件未安装时，原生桌宠仍能正常工作。

## 9.9 验收标准

- Live2D 模型可正常加载和渲染。
- 拖动、缩放、表情及基础交互稳定。
- 桌宠能够展示主系统任务状态。
- 屏幕感知未经授权无法执行。
- 撤销屏幕权限后采集立即停止。
- 屏幕感知异常不导致主程序崩溃。
- 桌宠关闭后不残留不必要的后台采集任务。
- 高资源负载时可自动降低动画负荷。

# 第十章 实验性桌面化与主题系统

## 10.1 桌面化目标

忆涟千言逐步成为 Windows 桌面的智能视觉与交互环境。

本轮不替换 Windows Explorer Shell，不接管操作系统的核心安全边界。

目标分为：

- 桌面主题。
- 壁纸引擎兼容。
- 桌面组件。
- 桌宠覆盖层。
- 实验性工作空间桌面。
- 后续应用挂载和多桌面协同。

## 10.2 Desktop Theme Orchestrator

统一管理桌面视觉状态。

职责：

- 识别当前壁纸提供者。
- 管理主题配置。
- 关联多显示器。
- 协调壁纸控制操作。
- 同步忆涟 UI 配色。
- 提供节能和性能模式。
- 管理异常恢复。

壁纸渲染与桌面主题编排必须解耦。

## 10.3 壁纸提供者模式

**Windows Native Provider**

使用系统接口管理原生静态壁纸。

**Wallpaper Engine Provider**

通过官方命令行控制能力接入。

优先实现播放、暂停、切换壁纸和可支持的配置操作。

**Lively Wallpaper Provider**

通过其公开控制接口接入。

**YiLian Internal Provider**

提供轻量内置壁纸渲染，供未安装外部壁纸软件的用户使用。

## 10.4 外部壁纸管理原则

每个显示器仅允许一个壁纸渲染主控。

忆涟不能在没有用户确认时关闭、卸载或替换外部壁纸软件。

切换提供者时需要：

1. 检查目标提供者状态。
2. 保存原有壁纸和相关配置快照。
3. 请求必要权限。
4. 停止或暂停冲突操作。
5. 应用新配置。
6. 检查结果。
7. 失败时恢复此前状态。

不得依赖未经稳定支持的 Windows 桌面窗口注入技巧作为正式发布功能的唯一实现。

## 10.5 动态主题

主题可以与壁纸状态关联。

支持：

- 明暗主题。
- 品牌色。
- 主辅色变化。
- 场景配置。
- 桌宠风格。
- 桌面组件视觉。
- 动画强度。

动态色彩可以来源于壁纸元数据、用户预设或授权分析。

用户必须能够锁定原有主题，不接受自动改变。

## 10.6 设计系统

继承「昔涟 · 涟漪」主题。

主要颜色：

| 名称 | 颜色 |
|---|---|
| 昔涟粉 | `#EA91B9` |
| 主色 Hover | `#DF7EAA` |
| 浅粉 | `#F9DCE9` |
| 涟漪紫 | `#AD9BE8` |
| 水色蓝 | `#99CFEA` |
| 夜色紫 | `#29263A` |

主题色应以设计 Token 方式统一管理，避免页面中大量硬编码颜色。

桌面允许更丰富的视觉效果，工作空间应优先保证文本可读性和长时间使用舒适度。

提供降低动态效果的选项。

实际软件界面展示使用真实截图或基于真实代码渲染的界面，不以生成式图片冒充产品完成效果。

## 10.7 桌面组件

第一批考虑：

- 桌宠。
- 任务状态。
- 时间与日程。
- 工作空间快捷入口。
- 系统状态。
- AI 快捷交互。

桌面组件应当具有独立生命周期，不能依赖打开完整主窗口才能正常展示。

## 10.8 Desktop Surface 实验

允许将一个受控的忆涟工作空间视图呈现在桌面环境中。

需要验证：

- 窗口层级。
- 多显示器。
- DPI 缩放。
- 焦点切换。
- 全屏应用兼容。
- Explorer 重启。
- 崩溃后回退。
- 桌面图标与任务栏共存。

所有实验功能必须可以通过安全模式关闭。

## 10.9 验收标准

- 支持原生壁纸模式。
- 能检测并接入至少一个第三方壁纸提供者。
- 能正确执行受支持的播放控制。
- 不与外部壁纸引擎抢占同一渲染层。
- 多显示器配置能够独立管理。
- 主程序退出后不会导致桌面不可用。
- 系统重启后主题配置与实际状态一致或能够明确降级。
- 实验功能可以独立禁用。

# 第十一章 开放生态兼容系统

## 11.1 开发目标

建立 `YiLian Ecosystem Bridge`，为外部软件提供统一能力接入路径。

不得将某个外部软件的专属 API 直接写入上层任务编排逻辑。

## 11.2 兼容等级

| 等级 | 名称 | 能力 |
|---|---|---|
| L1 | Discover | 发现、识别、状态检测 |
| L2 | Control | 通过官方接口执行操作 |
| L3 | Synchronize | 事件订阅与状态同步 |
| L4 | Integrate | 深度功能嵌入和双向交互 |

兼容等级取决于外部软件实际开放能力。

不能为了宣称支持 L4 而使用高风险、未授权或不稳定的接口。

## 11.3 标准适配器

建议核心方法：

`discover()`：发现应用或服务。

`connect()`：建立受控连接。

`capabilities()`：描述支持的能力。

`invoke()`：调用操作。

`subscribe()`：订阅支持的事件。

`health()`：检查可用性。

`disconnect()`：释放连接。

额外要求：

- 适配器版本。
- 外部软件版本。
- 权限声明。
- 错误码。
- 超时。
- 健康检查。
- 生命周期。
- 最低资源需求。
- 可选后台服务配置。

## 11.4 首批生态对象

| 对象 | 目标等级 | 主要能力 |
|---|---|---|
| Wallpaper Engine | L2，部分 L3 | 壁纸控制和可查询状态 |
| Lively Wallpaper | L2 | 壁纸控制 |
| Rainmeter | L2 | 桌面皮肤和组件命令 |
| VTube Studio | L3 | 角色状态及交互 |
| Codex | L3 | 任务、工具和会话事件 |
| Gemini CLI | L2–L3 | 结构化执行与结果同步 |
| Notion | L2，受控同步 | 页面读写 |
| Obsidian | L1–L2 | 本地库发现与文件访问 |
| MCP 服务 | 按能力声明 | 工具、资源与扩展能力 |

等级是目标，不代表已完成适配或每项功能都由软件官方保证。

## 11.5 兼容规则

所有适配器必须满足：

1. 外部软件缺失时正常降级。
2. 不默认接管用户已有配置。
3. 不擅自修改外部软件私有数据库。
4. 不绕过外部程序本身的授权。
5. 不复制外部服务凭据到主配置文件。
6. 外部连接失败不能影响主系统核心服务。
7. 支持断开连接和撤销授权。
8. 应支持能力发现，而不是仅通过固定软件名称调用。
9. 对外部 API 的不兼容更新提供版本检查。
10. 具备最小可运行的集成测试。

## 11.6 插件 SDK

建议向开发者提供：

- 插件元数据规范。
- 能力声明规范。
- 权限清单。
- 工具调用接口。
- 事件订阅接口。
- 资源访问接口。
- 用户界面扩展点。
- 后台服务生命周期接口。
- 测试框架。
- 示例插件。

插件可携带后台服务，但应按需启动，并由统一资源管理器管理。

对于本地与云端 Harness，应根据宿主环境分别声明所需的依赖、权限和运行条件。

# 第十二章 权限与安全系统

## 12.1 授权模型

继续采用三层管理概念：

- 超级权限。
- 用户级权限。
- 忆涟级权限。

实际授权应进一步细分为具体 Capability。

例如：

`screen.capture`、`microphone.read`、`file.read`、`file.write`、`process.execute`、`network.access`、`desktop.control`、`memory.write`。

不能因为某个插件属于忆涟生态，就自动继承全部超级权限。

## 12.2 权限作用域

每项授权应包括：

`principal、capability、resource_scope、effect、expires_at、policy_version、grant_source`。

权限有效范围可设为：

- 单次操作。
- 当前任务。
- 当前会话。
- 指定项目或目录。
- 特定应用。
- 长期授权。

高风险操作应支持二次确认。

## 12.3 权限撤销

撤权必须同时影响：

- 尚未执行的请求。
- 活跃感知会话。
- 可被终止的后台任务。
- 新生成的上下文。
- 缓存和索引访问。
- 外部软件连接。

对于已经执行的不可逆操作，需要明确结果，而不是虚假声明全部回滚。

## 12.4 凭据管理

API Key、CLI 授权令牌和第三方服务凭据不应以明文存储在普通 SQLite 配置表或日志中。

Windows 优先采用 Credential Manager 或 DPAPI 等系统凭据保护方式。

跨设备迁移时需要独立处理凭据重新授权问题。

## 12.5 富交互安全

聊天 UI 采用 Schema 白名单渲染。

禁止：

- 直接执行模型生成的任意脚本。
- 在组件事件中无授权访问文件。
- 组件跨用户读取上下文。
- 不受控制地打开外部链接。
- 在沙箱中直接暴露宿主高权限接口。

## 12.6 外部内容安全

聊天记录、网页内容、文档和外部工具结果都可能包含不可信指令。

系统必须将这些内容作为数据处理，不能因为某个文件或网页写有“执行某命令”，就将其提升为系统指令。

具有文件写入、命令执行、网络发送能力的 Agent 操作需要独立策略检查。

# 第十三章 资源调度与运行优化

## 13.1 Resource Orchestrator

统一管理：

- 本地模型进程。
- Embedding 推理。
- CLI 子进程。
- 桌宠渲染。
- 动态壁纸联动。
- 外部适配器后台服务。
- 大型工作空间任务。
- 其他可管理执行器。

## 13.2 资源生命周期

采用：

**Active**：正在使用。

**Warm**：可快速恢复，保留必要状态。

**Cold**：进程不运行，仅持久化恢复信息。

所有执行器必须声明哪些状态可持久化，哪些只能保留在运行进程内。

## 13.3 本地性能原则

目标硬件基线包含 RTX 4050 6GB 与 16GB 内存的个人电脑。

需要重点防止：

- Embedding 模型长时间占据显存。
- Live2D 渲染与大型模型推理互相争抢资源。
- 外部壁纸引擎和内置桌面渲染器重复工作。
- 多个 CLI 无限制并行启动。
- 页面树和聊天记录全部装入内存。
- 大规模向量重建堵塞普通界面。

高负载时应优先保证用户操作响应和正在执行的重要任务。

桌面动画及非紧急后台索引任务应当可以降级或暂停。

## 13.4 资源预算

资源预算使用配置化策略，不在代码中写死适用于所有设备的单一阈值。

需支持：

- 自动检测设备档位。
- 用户手动调整资源策略。
- 性能优先、平衡、节能模式。
- 任务优先级。
- 进程并发上限。
- 后台任务限速。
- 资源压力事件通知。

# 第十四章 数据库与持久化规范

## 14.1 存储分层

**SQLite 主库**

保存用户、会话、页面、记忆原文、任务、权限和适配器状态。

**SQLite FTS5**

全文索引。

**Vector Index**

保存派生向量。

**Asset Store**

存储图片、附件及其他二进制资源。

**Cache Store**

保存可重建的上下文缓存、缩略图和中间结果。

## 14.2 推荐核心表

| 领域 | 核心数据表 |
|---|---|
| 用户 | `user_profiles`, `onboarding_progress`, `profile_facts` |
| 会话 | `conversations`, `conversation_branches`, `conversation_events` |
| 模型 | `model_providers`, `provider_sessions`, `context_snapshots` |
| 记忆 | `memory_items`, `memory_revisions`, `memory_relations`, `memory_embedding_refs` |
| 工作空间 | `workspaces`, `pages`, `page_blocks`, `page_revisions`, `page_links` |
| 任务 | `task_executions`, `tool_executions`, `task_checkpoints` |
| 生态 | `adapter_installations`, `adapter_connections` |
| 权限 | `permission_grants`, `permission_audit` |
| 桌面 | `desktop_profiles`, `wallpaper_bindings`, `surface_instances` |
| 资源 | `assets`, `asset_references`, `background_jobs` |

这是目标数据模型，不要求已有数据迁移到同名表。

## 14.3 数据库约束

要求：

- 主键稳定。
- 外键关系明确。
- 事件流顺序具备唯一约束。
- 页面树防止循环引用。
- 内容块维护修订号。
- 对大量历史记录使用索引和分页。
- 删除行为具有可预测的级联规则。
- 向量记录保存模型和维度信息。
- 关键操作通过数据库事务提交。

## 14.4 资源文件管理

使用内容摘要或稳定资源 ID 识别附件。

实现：

- 文件引用计数或引用查询。
- 重复资源去重。
- 文件完整性检测。
- 缩略图缓存。
- 无引用文件回收。
- 文件迁移与路径重定位。

不直接依赖绝对路径作为资源唯一身份。

## 14.5 数据迁移

数据库升级必须通过显式迁移脚本。

流程：

1. 检测数据库版本。
2. 执行完整性检查。
3. 备份重要持久化数据。
4. 执行版本迁移。
5. 验证主键、外键与记录数量。
6. 重建必要的派生索引。
7. 更新 Schema 版本。
8. 执行回归验证。

对于无法直接回滚的 Schema 更改，优先采用备份恢复及兼容发布策略。

不得通过删除数据库重新创建来解决正式环境的迁移问题。

# 第十五章 API 与内部服务契约

## 15.1 基本原则

优先延续已有 API 风格。

下面路径仅作为拟定契约示例。

所有接口应具备稳定错误码、权限校验和版本控制。

## 15.2 初始化接口

`GET /api/v1/onboarding/status`

获取初始化状态。

`POST /api/v1/onboarding/steps`

提交当前初始化步骤。

`POST /api/v1/onboarding/complete`

完成初始化。

`GET /api/v1/profile`

获取用户资料。

`PATCH /api/v1/profile`

修改用户资料。

## 15.3 会话与模型

`POST /api/v1/conversations`

创建会话。

`GET /api/v1/conversations/{id}/events`

分页或按游标读取事件。

`POST /api/v1/conversations/{id}/turns`

发送新轮次。

`POST /api/v1/turns/{id}/cancel`

取消轮次。

`GET /api/v1/models/capabilities`

获取模型能力。

`POST /api/v1/conversations/{id}/provider-switch`

切换提供者。

## 15.4 记忆

`POST /api/v1/memory/search`

检索记忆。

`GET /api/v1/memory/{id}`

读取记忆与来源。

`PATCH /api/v1/memory/{id}`

修改记忆。

`DELETE /api/v1/memory/{id}`

发起记忆删除。

`POST /api/v1/memory/index/rebuild`

创建重索引任务。

## 15.5 工作空间

`GET /api/v1/workspaces`

获取工作空间。

`POST /api/v1/pages`

创建页面。

`GET /api/v1/pages/{id}`

读取页面。

`PATCH /api/v1/pages/{id}`

修改页面元数据。

`POST /api/v1/pages/{id}/blocks/patch`

提交内容块变更。

`GET /api/v1/pages/{id}/revisions`

读取版本记录。

## 15.6 生态与桌面

`GET /api/v1/ecosystem/adapters`

列出适配器。

`POST /api/v1/ecosystem/adapters/{id}/connect`

建立连接。

`POST /api/v1/ecosystem/capabilities/invoke`

请求能力调用。

`GET /api/v1/desktop/providers`

列出桌面提供者。

`POST /api/v1/desktop/theme/apply`

应用主题。

`POST /api/v1/perception/sessions`

发起感知会话。

`DELETE /api/v1/perception/sessions/{id}`

结束感知。

## 15.7 并发控制

页面编辑、配置修改和交互组件状态变更应使用版本号检查。

发生冲突时返回明确冲突状态，要求客户端刷新或执行合并。

不能采用最后一次写入永远覆盖前一次写入的简单策略处理所有数据。

## 15.8 事件流

支持客户端按事件游标重新连接。

至少需要：

- 事件序号。
- 消息类型。
- 有效载荷。
- 心跳。
- 完成状态。
- 错误状态。
- 恢复游标。

流断开不代表任务一定终止。

前端重连时应先查询真实任务状态，避免重复发送执行请求。

# 第十六章 用户界面与交互规范

## 16.1 全局界面结构

维持主界面统一导航，避免因增加大量功能而创建大量相互隔离的页面。

建议一级入口：

- 聊天。
- 工作空间。
- 任务。
- 记忆。
- 插件与生态。
- 设置。

桌宠和桌面环境属于独立 Surface，不要求成为普通一级页面。

## 16.2 设置体系

默认全局配置。

仅在确有需要时允许项目级、会话级及适配器级覆盖。

所有局部覆盖必须在界面中显式标明。

优先级与继承关系应有统一解释，不允许每个模块自行定义覆盖逻辑。

## 16.3 初始化界面

采用循序渐进的交互。

页面应支持跳过、返回、保存草稿与重新进入。

不应一次要求用户输入大量非必要信息。

## 16.4 聊天界面

应清楚展示：

- 当前模型与提供者。
- 消息内容。
- 多模态资源。
- 工具及任务执行状态。
- 需要审批的操作。
- 可保存成果。
- 可交互组件。
- 模型切换。
- 会话分支。

可使用独立的任务详情区域展示长流程执行。

## 16.5 工作空间界面

采用树形导航、内容区域和可选辅助面板。

页面编辑区域应具有足够空间，支持沉浸式编辑。

## 16.6 桌面与桌宠

桌宠需要在不打断主要工作的情况下提供帮助。

界面应支持勿扰状态、位置记忆、透明度、缩放和显式关闭。

桌面主题需要分别管理壁纸提供者和忆涟视觉 Token。

## 16.7 UI 规范

- 保持昔涟主题识别度。
- 尽量复用已有组件与图标体系。
- 支持明暗模式。
- 提供键盘操作。
- 保证必要的文本对比度。
- 动画尊重系统减少动态效果设置。
- 功能操作应提供明确结果反馈。
- 实验功能应有标识与关闭入口。

# 第十七章 监控、日志与故障恢复

## 17.1 日志等级

建议使用：

`TRACE、DEBUG、INFO、WARN、ERROR`。

区分普通诊断日志与安全审计日志。

默认不在日志中保存原始屏幕截图、API 凭据或用户的完整敏感文档。

## 17.2 核心观测指标

记录：

- 会话事件提交状态。
- 模型请求耗时。
- CLI 执行状态。
- Token 使用量（如可获取）。
- 缓存命中情况。
- 向量索引队列。
- 记忆检索耗时。
- 页面保存失败次数。
- 插件连接状态。
- 桌宠渲染性能。
- 系统资源压力。
- 崩溃和恢复结果。

## 17.3 失败恢复原则

**模型失败**

保留完整用户请求，允许切换提供者后继续。

**CLI 失败**

记录执行到哪一步，恢复前判断副作用。

**数据库失败**

停止危险写入，提供可诊断错误信息，并保护备份。

**插件失败**

隔离插件，降级对应功能。

**桌宠失败**

关闭桌宠窗口，不影响主程序。

**壁纸控制失败**

保持原壁纸或恢复用户此前的配置。

**屏幕采集失败**

终止采集会话并释放系统资源。

## 17.4 任务恢复信号

任务应明确产生：

- 开始信号。
- 阶段更新。
- 审批等待。
- 暂停。
- 恢复。
- 完成。
- 失败。
- 取消。

用户必须能够区分“任务仍在执行”和“任务已异常停止”。

# 第二十章 风险、约束与兼容策略

## 20.1 最大架构风险：会话和上下文耦合

如果继续以模型原生会话作为唯一记录来源，跨模型切换将长期困难。

解决方法：

统一可观察事件存储，Provider Session 仅维护外部会话映射。

## 20.2 最大数据风险：记忆与会话互相污染

如果将每条聊天记录自动提升为长期记忆，记忆质量会迅速下降。

解决方法：

候选提取、重复检查、来源追踪、权限过滤和版本管理。

## 20.3 最大工程风险：多套重复系统

如果桌宠、工作空间、聊天和 CLI 分别拥有消息队列、权限管理和模型接口，维护成本将急剧增加。

解决方法：

复用统一事件、上下文、任务及权限体系。

## 20.4 最大桌面风险：破坏 Windows 原生桌面

不稳定的桌面窗口层集成可能引发图标异常、焦点问题或 Explorer 冲突。

解决方法：

桌面实验独立进程、可关闭、可恢复，不替换系统 Shell。

## 20.5 最大生态风险：第三方接口变化

外部 CLI、壁纸引擎和第三方 API 可能更新或改变行为。

解决方法：

适配器版本检测、能力协商、官方接口优先和兼容测试。

## 20.6 许可证与内容资产

Live2D SDK、第三方角色模型、创意工坊壁纸、编辑器扩展和外部软件均需要分别检查其使用和分发条款。

兼容外部应用不等于获得重新分发其软件或内容资产的权利。

## 20.7 Web 与桌面能力差异

Web Surface 不应被要求执行只有 Windows 原生客户端才能完成的操作。

统一模型必须允许能力缺失。

例如 Web 可以展示桌宠和工作空间，但没有对应权限或本地桥接时不能直接操作 Windows 桌面。

# 第二十二章 最终完成定义

本轮升级完成后，系统应表现为一个连续的个人智能工作环境。

用户首次启动软件时，能够完成个人化初始化。

此后，用户在聊天中与不同模型协作，无论模型来自 API、CLI 还是本地运行时，忆涟都通过统一会话系统维护可观察的上下文。

模型能够生成文字、图片、图表及可交互组件。

用户可以将成果保存到无限页面工作空间，并在后续任务中继续引用。

记忆系统通过本地向量化与混合检索理解历史信息，同时允许用户管理、修正和撤回长期记忆。

桌宠能够在用户授权的范围内感知任务和屏幕，并作为一个常驻交互入口连接主系统。

桌面层能够兼容 Wallpaper Engine、Lively Wallpaper 和其他成熟外部软件，提供统一的视觉主题和交互组件，而不要求用户放弃现有应用。

外部软件通过 Ecosystem Bridge 被识别、授权和调用，逐步成为忆涟千言可编排的能力节点。

最终产品应满足：

**一个用户体系、一个会话事实来源、一套上下文编排、一套记忆体系、一套权限与资源管理机制、多种交互界面、多个可替换的模型和外部软件提供者。**
