## 数据迁移

旧程序建立的 SQLite 档案预先保存一段会话、一条带中文正文的消息和一个配置项。新版第一次打开旧档案时，通过在线备份保留旧库，运行迁移、启动 API，再核验三个原始值。另把备份复制为独立数据库进行旧结构检查。两份库的 `PRAGMA integrity_check` 返回 `ok`，`PRAGMA foreign_key_check` 返回零条记录。

实际旧库使用第 1091 号迁移的 Windows CRLF 摘要。它与当前 checkout 中同一 SQL 的 LF 摘要不同。修复保留旧摘要并认可相同内容的另一种换行写法，实测从上述旧库升级成功。作业失败后重试会优先复用已校验的升级前备份。

## 中断与恢复

在单独的临时账号中持续运行 **907.6 秒**。以真实 HTTP 写入个人配置修订并按游标回读，累计 540 次请求、180 次已提交变更。测试中间强制终止自己的后端子进程，再以同一数据目录重启。会话作用域、修订和事件序列保持连贯，检查中没有重复或缺失的事件。此样本使用 00:53:50 的测试构建；最终构建与各专项套件结果见同目录的验收报告。覆盖时长为 15 分钟。

## 复现

使用 `scripts/qa/verify-capability-upgrade.py` 的 `seed` 与 `verify` 子命令生成和检查旧档案。使用 `soak <后端可执行文件> <新的隔离目录> --seconds 900` 复现中断恢复。脚本只终止其自身启动的子进程。
